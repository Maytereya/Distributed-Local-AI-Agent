На origin есть ветки `split-long-messages`, `split-long-messages-from-api`,

fetch выполнить **на сервере** от имени владельца deployment-ключа в отдельные
audit refs и сравнить merge-base/коммиты/пути; не копировать базу и `.env`.

## Порядок объединения

### 1. Зафиксировать базу и действующие версии

1. Повторно прочитать HEAD обоих репозиториев и безопасный manifest запущенных
   контейнеров. Если есть новые коммиты/образы, пересчитать сравнение до выкладки.
2. Сохранить локальную копию текущих staged/working patches и список файлов
   отдельно от секретных untracked. На сервере сохранить Compose/конфигурации
   защищённо и свежий дамп перед следующей миграцией.
3. Согласовать с разработчиком репозиторий, рабочую ветку, незапушенные изменения
   и окно выкладки. Наличие live checkout HEAD не равно составу Docker-образа;
   сверять исходники и ID образов отдельно.

### 2. Подготовить две изолированные ветки

Ветки начинать от **свежего upstream**, в отдельных worktree; не выполнять
`pull`, reset или массовый merge поверх нынешнего изменённого checkout.

| Ветка / PR | Состав |
| --- | --- |
| RAG, база `release` | Авторизация/приватные логи, безопасная ошибка валидации, reporting contract/facts, тонкие изменения пяти файлов маршрутизации, необходимые общие модули и их тесты |
| Агрегатор, база `main` | Серверные права HTTP/WS/вложений, безопасные логи/TLS, receipts/связи/передача, `core.0009`, приложение reporting с миграциями, worker и ручная проверка |
| Инфраструктура и документы | Monitor/broker/plugin/sandbox/egress, закреплённые Dockerfile/override, безопасные шаблоны настройки и журналы; сохранять утверждённые параметры доступа |

Не переносить весь июльский файл туда, где достаточно нескольких изменений.
Не включать пользовательские price/Compose правки без отдельной сверки.
Для общей библиотеки схемы выбрать один источник версии: небольшой общий
пакет либо проверяемое копирование с закреплённым SHA. Не держать две
независимо редактируемые копии контракта.

### 3. Разрешать смысловые пересечения

| Область | Что сохранить и проверить |
| --- | --- |
| Endpoint | Кнопки, warm-up, `user_text`, streaming/once, безопасная авторизация/валидация, final reporting только для завершённого ответа |
| Router/orchestrator | Последние детерминированные ответы, исправления МИС, уточнения, context action и признаки составного вопроса; reporting добавляется после актуального recovery |
| Recovery | Отказ оператора не превращается в запрос; срочность монотонна; нет данных не маскируется свободным ответом ИИ |
| Цена и расписание | Пустые результаты, новые поля врача, отсутствие расписания и уточнения сохраняют свежие исправления разработчика |
| Отправка / streaming | Receipt каждой отправки/части; неясная отправка не повторяется автоматически; все финальные сообщения и документы связаны с turn |
| Параллельные сообщения | Блокировки conversation → turn → appeal, дедупликация внешнего update, отсутствие дублированного handoff/нового обращения |
| Редактирование | Сохранение `edited_at`; подпись доказательств инвалидирует модельный кеш и ручную оценку |
| Docker/сети | Разделение proxy по ролям, `br_netfilter`, IPv6, secrets owner/mode, worker без `.env`; не вернуть старые socket/привилегии при merge |

Следовать актуальным
[`docs/ARCHITECTURE_PRINCIPLES.md`](https://github.com/Maytereya/Distributed-Local-AI-Agent/blob/6b4fabf309b8b3dc3ae812cc239933d3933c9389/docs/ARCHITECTURE_PRINCIPLES.md):
факты из МИС печатает код, LLM выбирает из закрытого множества,
отсутствие данных и срочность обрабатываются явно. Новые счётчики не должны
менять эти правила.

### 4. Проверить объединённый результат

- Тесты обоих upstream и наши явные наборы безопасности/учёта; не использовать
  общий discover, способный вызвать старую интеграцию с клиническими данными.
- Синтетические price + schedule, результаты, справка, кнопки и уточнения,
  отказ → решение, передача/взятие, timeout, PDF, split/edit, параллельные turn.
- Реальный PostgreSQL 16 в изолированном окружении: миграции, блокировки,
  дедупликация. Синтетическая тестовая БД; восстановление дампа проверять
  отдельно на сервере, без передачи пациентских данных в CI.
- Canary API/UI без второго Telegram poller и без рабочей рассылки;
  повтор отрицательных сетевых/роль/лог/injection сценариев.
- PID/context/options Ollama и время пациентских ответов при синтетическом
  анализе. Никакого массового фонового обхода до ручной приёмки.

Публиковать только очищенный diff. Задачи и PR описывают поведение,
синтетическое воспроизведение, миграции, проверки и откат; живую переписку
и секреты в текст не включать.

### 5. Выкладка и откат

1. Закрепить коммит, зависимости, image ID/digest и Compose каждого компонента.
2. Применить добавочные миграции, сохранив старые таблицы и данные.
3. Обновлять отдельные компоненты с healthcheck; оставлять один пациентский
   poller. API/UI отчётности можно обновлять без его перезапуска.
4. Проверить fresh worker, начало учёта, баланс, очередь, типовые ответы,
   ожидаемые расписания и receipts; повторить проверку egress.
5. При ошибке вернуть сохранённый образ и совместимую защищённую конфигурацию.
   Новые события/колонки оставить. **Старый дамп поверх живой БД не является
   обычным откатом**: он уничтожит новые пациентские сообщения.
