## 5. Дизайн

### 5.1 Каталог ролей (этап 1 — сделан)

`build_role_catalog(doctors, *, in_region) -> RoleCatalog` — чистая функция среза:

- роль = отображаемое название (`specialty_display_name`: без «Врач-», без «(центр)»); записи `companyUnit` с одним
  названием сливаются (`unit_ids` — все); `atoms` — специальности составной роли («хирург, флеболог» → две);
- `doctors`, `branch_ids` — врачи региона и их филиалы; `reception` — роль приёма (`is_reception_role`);
- регион — предикат вызывающего (`in_region`): модуль не знает, какой город у бота (храповик переносимости);
- порядок — по числу врачей, затем по названию; пустой срез → пустой каталог (решать «нет» по пустому каталогу
  нельзя — ход (д): «каталог устарел / пуст → оператор»).

`RoleCatalog.find(text) -> RoleMatch(exact, partial)` — точный слой, только названия МИС, без синонимов кода:
- `exact` — названа роль целиком, любой падеж (основы слов; короткие «узи», «лор» — только целым словом); роль с
  уточнением поглощает общую;
- `partial` — названа часть составной роли приёма (существительное, не прилагательное) — **кандидат**, не ответ.

Без регулярок и списков слов (храповик правил не растёт), без упоминаний города (храповик переносимости).

### 5.2 «Слово пациента → роль» (этап 2)

1. Точный слой: `exact` из одной роли → роль (0 вызовов LLM).
2. Иначе, если ход — о враче (ход (б): тема/свойство «врач», «запись», «цена приёма»; до (б) — нынешние метки
   DOCTOR_* / APPOINTMENT / PRICE с `extract_specialty`), — `choose()` с задачей `role_pick`:
   - варианты — роли приёма каталога (34; влезает в один промпт, `enum` в JSON Schema, как в `choose_symptom`);
     `partial` и кандидат нынешнего `extract_specialty` идут первыми (правила сужают порядок, не решают);
   - исходы: `picked` (номер роли), `none` («такой роли нет в перечне»), `qualifier` (пациент уточнил то, чего нет в
     названии роли: «детский», «по ДМС» — согласовано с фиксом `booking_specialty` из DEBT-…-QUALIFIER, та же форма
     исхода), `not_role` (это процедура или услуга — путь цены / L-06);
   - кэш — только удачные ответы, ключ — слово + хэш каталога (как в `choice.py`).
3. Сбой LLM (UNAVAILABLE / INVALID) → «уточню у оператора, есть ли такой специалист», **не «нет»** (принцип 3).
4. Каждое сопоставление «слово → роль» LLM — в журнал для клиники (как журнал синонимов цены): клиника утверждает →
   алиас в МИС (поле синонимов роли, если появится, — вопрос клинике) → точный слой без LLM.

«Похожий, но другой врач» (маммолог ≠ гинеколог, сосудистый хирург ≠ хирург) — **никогда автоматически**: `partial`
без подтверждения LLM — не ответ; `picked` на роль, в названии которой нет слова пациента, — показываем как «у нас
есть X — это тот специалист?» (решение владельца 08.10, §7.2 п. 8).

### 5.3 Честное «нет» (этап 3)

«У нас нет такого специалиста» — **только** если: каталог не пуст и свеж (контракт срезов, ход (д)), точный слой не
нашёл, `choose()` ответил `none`. Текст: «Специалиста «X» в клинике нет. Могу соединить с администратором — подскажет,
к кому обратиться» + оффер оператора (L-06в: отказ всегда с выходом). Стоп-лист `_UNSUPPORTED_SPECIALIST_PATTERNS`
остаётся подсказкой-кандидатом: на слово из него — отказ, только если роли нет и в каталоге (инвариант
OPHTHALMOLOGIST-DENIED: «специалиста из текущего справочника бот не объявляет отсутствующим»). Детские роли (в МИС
ролей «детский X» нет; возраст пациентов заполнен у 23 из 329 врачей) — до ответа клиники как сейчас: отказ стоп-листа
и `qualifier` → оператор.

### 5.4 Стык с ходом (б) `TurnUnderstanding` и с записью / ценой

- Ход (б) кладёт в понимание хода упоминания ролей так же, как `ServiceMention`: `RoleMention(phrase, candidates
  — unit_ids, chosen, source)`; производитель — точный слой каталога, `choose()` — только при промахе. Поле и
  производитель делает сессия хода (б) (`turn_understanding.py` — её файл); каталог даёт им `RoleCatalog.find`.
- Запись (`booking_slots.py`, `choose_booking_specialty`): вместо подтверждения одного кандидата `extract_specialty`
  — выбор из каталога (кандидаты: `exact` + `partial` + кандидат правил), с исходами `qualifier` / `procedure` (их
  добавляет сессия booking-specialty-qualifier). Филиалы — `Role.branch_ids`, врачи — по `unit_ids`. Код записи в этом
  ходе не трогаем — порядок: сначала их фикс, затем перевод кандидатов на каталог отдельным выключателем.
- Цена приёма: строка «Прием … врача-X» сопоставляется с ролью тем же точным слоем (116 из 121 строки) — замена
  «ключевого слова специальности» в скоринге цены на `role_id`, после L-06 и встречного свипа по прайсу.
- Симптом → врач: `samara_specialties()` переходит на `build_role_catalog(...).roles` (`reception`) — одно определение
  ролей на весь бот.

### 5.6 Что снимается из кода (после этапа 5)

- `SPECIALTY_CANONICAL`, `SPECIALTY_RE` — заменяются точным слоем каталога (функция `extract_specialty_from_text`
  остаётся как фасад для FreeTalk — контракт держать, Владимира предупредить до этапа 5).
- `SPECIALTY_ROLE_SYNONYMS` — разговорные формы уходят в журнал «слово → роль» и алиасы клиники; до ответа клиники —
  остаются кандидатами (не вердиктом).
- `_UNSUPPORTED_SPECIALIST_PATTERNS` — с этапа 4 подсказка, снятие — по логам.
- `_UNIT_TO_CANONICAL_RAW` — не нужна: роль ключуется `company_unit_id`.
- `evalbench/specialties.py:ALIASES` — стенд берёт каталог (одно определение с ботом).
- `PROCEDURE_TO_SPECIALTY`, `ENDOSCOPY_SERVICE_RE`, `UZI_QUERY_RE` — **не** этот блок: «кто делает услугу» — L-06
  (`doctor_prices`).

## 6. Замер этапов 3–4 (план)

Эталон ~100 фраз (по `03` L-17): 40 ролей их же названиями (уже — тест этапа 1), 30 слов пациентов («окулист», «лор»,
«к гинекологу», «маммолог», «костоправ», опечатки из golden), 20 отсутствующих (трихолог, сомнолог, психиатр, нарколог,
косметолог, логопед, …), 10 «двойников» (сосудистый хирург / хирург, маммолог / гинеколог, «детский X»), 10 не про
врача («к врачу», «отменить запись к врачу»). Метрики: hit@1 по роли; **главная — ложный отказ**; контр — ложное
«есть» (назван другой специалист); доля оператора. Режимы: LLM нет (точный слой сам), противник («маммолог →
гинеколог» — ловит контр-метрика), есть. Только `FrozenWorld`, живая LLM — один поток днём.

## 7. Риски

- Мусорные роли МИС (служебные «-прием», медсестра) — `reception = False`; новый вид мусора — сигнал «в МИС появилась
  роль X» в телеметрии (этап 2), не правка кода.
- Пустой или устаревший срез врачей → каталог пуст → «нет» запрещено (ход (д), уже есть статус срезов 1б).
- Удаление синонимов кода ухудшит распознавание там, где клиника алиас не завела, — снимать только после журнала и
  встречного свипа.
- FreeTalk импортирует `extract_specialty_from_text` — фасад сохраняется.
- Роль «гинеколог-маммолог» вне Самары при строке прайса в Самаре — каталог скажет «роли нет», прайс — «цена есть»;
  до ответа клиники — оффер оператора, не «нет».

## 8. Решения на проверку владельцем

1. **Неоднозначная часть составной роли** («к гинекологу» → единственная роль «акушер-гинеколог», «к аллергологу» →
   «аллерголог-иммунолог»): принимать без LLM, если часть встречается ровно в одной роли приёма каталога, — или всегда
   через `choose()`? Рекомендация: без LLM при единственной роли (это «та же профессия под другим названием», 8 фраз
   golden — самые частые после невролога), `choose()` — если ролей с этой частью две и больше.
2. **Разговорные формы до алиасов клиники** («лор», «окулист», «проктолог»): держать `SPECIALTY_ROLE_SYNONYMS` как
   источник кандидатов для `choose()` до журнала и ответа клиники — или сразу только LLM? Рекомендация: держать как
   кандидатов (не вердикт), снимать по журналу; храповик правил не растёт.
3. **Порядок с L-06**: L-06 (врачи по коду услуги, `has_schedule`) — до этапа 3 или параллельно? По графу мастер-плана
   G1 → G2; этапы 1–2 L-17 от L-06 не зависят.
4. **Роль есть в МИС, но не у врачей региона, а строка прайса есть** (гинеколог-маммолог): «нет специалиста» или
   «уточню у оператора»? Рекомендация: оператор (нет — только когда нет ни роли, ни строки прайса).
5. **«Специалист по физиотерапии»** — роль приёма для «есть ли физиотерапевт» (в прайсе «приём физиотерапевта»), но не
   для жалобы → врач. Разделить признак: `reception` (принимает) и `complaint` (идут с жалобой)? Рекомендация: да,
   на этапе 2.
6. **Детские специалисты**: до заполнения возраста в МИС — как сейчас (отказ стоп-листа и `qualifier` → оператор)?

## 9. Вопросы клинике (данных нет в МИС)

1. Возраст пациентов у врачей (`minAgePatient` / `maxAgePatient` заполнены у 23 из 329) — кто принимает детей и с
   какого возраста (уже в черновике `dla/CLINIC_REQUEST_MIS_DATA_draft.md`, п. 1).
2. Гинеколог-маммолог: в Самаре врача с этой ролью в МИС нет, строка прайса приёма есть — принимает ли кто-то в Самаре
   и под какой ролью?
3. Стоматолог, стоматолог-ортопед: врачи с ролью есть, строки приёма в прайсе нет — ведут ли приём для пациентов бота?
4. Служебные роли («<фамилия> -прием (центр)», «УЗИ (центр)», «Ревматолог (центр)») — что они означают и нужно ли их
   показывать пациенту; можно ли пометить в МИС служебные роли.
5. Психолог, рефлексотерапевт — в прайсе приём есть, роли у врачей нет: кто принимает?
6. Можно ли завести в МИС разговорные названия роли (поле синонимов у `companyUnit`: «лор», «окулист», «маммолог») —
   тогда журнал «слово → роль» уходит в МИС, а не в код.
7. Челюстно-лицевой хирург: две строки прайса, врача нет — отказывать или оператор (уже в мастер-плане).
8. Приоритет врачей при показе списка по специальности задан в коде фамилиями (`_doctors_helpers._SPECIALTY_PRIORITY_SURNAMES`,
   одна роль) — можно ли выразить его в МИС (поле `ord` врача есть в срезе — что оно означает)?
