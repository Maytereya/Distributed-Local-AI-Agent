# `messengers_router` — журнал багов (anti-regression log)

**Зачем:** все присланные «живые» баги фиксируются здесь, чтобы код не регрессировал и баг не приходил повторно. Ключевой принцип — **записываем не только инстанс, но и обобщённый инвариант** (класс бага), и покрываем его **тестом на класс**, а не на конкретный случай.

**Почему не только тесты:** инстанс-тест (на «Турмухамбетова») ловит один случай — другой несамарский врач воспроизведёт баг, а тест пройдёт. Поэтому:
1. **Тест на КЛАСС/инвариант** — параметризованный, или сканирует live-кэш и выбирает отсутствующего, или использует синтетическое значение, гарантированно попадающее в класс.
2. **Локальные тесты держат детерминированную логику; remote eval держит live/LLM-поведение** (то, что локально не воспроизвести). Golden-кейсы в `eval_suite/` добавляются по решению владельца.
3. Запись здесь = «память проекта» по багам (версионируется, видна команде, переживает сессии).

**Формат записи:** симптом (как прислал пользователь) · корень · фикс-коммит · **инвариант** · покрытие (тест/eval).

## BUG-2026-06-02-08 — compound-УЗИ (>1 органа): подбор одной услуги / игнор добавлений

- **Симптом (live):** «записаться на узи жтк + почки» → бот подбирал ОДНУ услугу (часто чужую). В активной УЗИ-записи follow-up'ы «А плюс поджелудочная», «И плюс почки» игнорировались (бот залипал на «печени и желчного»).
- **Корень:** не баг матчинга, а **отсутствие обработки** набора из нескольких УЗИ. В каталоге комбинированные УЗИ — отдельные позиции; generic-композиции «УЗИ X + УЗИ Y» нет, compound-флоу для УЗИ-записи не было (только для lab-анализов). Поэтому набор сваливался в одиночный матч/игнор.

- **Инвариант (класс):** УЗИ-запись с >1 органом (УЗИ-контекст из реплики ИЛИ активной услуги + ЯВНЫЙ additive-маркер `+`/`плюс`/`ещё`) → оффер оператора. Каталожные «и»/«,» внутри одной позиции («УЗИ печени и желчного пузыря») compound НЕ считаются. Детектор-regex ReDoS-безопасен (квантификаторы `{3,}` только ПОСЛЕ обязательных литералов).

## BUG-2026-06-02-06 — дата DD.MM.YYYY распознаётся как время «HH:MM»

- **Симптом (live):** в активном APPOINTMENT-флоу «На 03.06.2026» → бот подтверждал «… 3 июня, **03:06**» (запись на 3:06 ночи). Дата прочитана и как время.
- **Корень:** `parse_date_time_ru` ([policies.py](../messengers_router/policies.py)) сначала парсит дату (верно), затем отдельно время — а time-регэкспы (`_QF_TIME_RE` и др.) используют разделитель `[:.]` (двоеточие ИЛИ точка), поэтому «03.06» из даты «03.06.2026» ловится bare-time-регэкспом как «03:06». Дата и время извлекались из одного текста независимо.
- **Инвариант (класс):** распознанная ЦИФРОВАЯ дата (`DD.MM[.YYYY]` / ISO) не должна порождать ложное время. Время ищем по тексту, из которого вырезаны фактические спаны валидных цифровых дат. Обратная сторона: валидное время с точкой («в 15.30», «15.30») НЕ вырезается (как дата «15.30» невалидна — месяц 30) → остаётся временем. Критерий по фактически распознанной дате (спан), не по «есть точка».
- **Фикс-коммит:** `f90a425` (в `parse_date_time_ru` копим `consumed_date_spans` при валидной DOT/ISO-дате; перед поиском времени строим `time_text` с вырезанными спанами; все 5 time-регэкспов ищут по `time_text`).
- **Покрытие:** `tests/test_date_parsing.py` — `test_dotted_date_does_not_produce_spurious_time` (DD.MM[.YYYY]/ISO → date без time), `test_dotted_time_still_parsed` («в 15.30»/«15.30»/«к 9»/«с 9 до 18» → time), `test_date_and_explicit_time_both_parsed` («03.06.2026 в 9» → дата+время). Локально 867 passed, ruff clean. **Live «после» — после деплоя** (в активной записи «На 03.06.2026» → дата без 03:06).
