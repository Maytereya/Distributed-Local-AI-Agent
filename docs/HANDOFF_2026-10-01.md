## 6. Ошибки этой сессии — чтобы не повторить

- **Слой LLM проектировал раньше, чем собрал стенд для свипа.** Каждая «простая» версия
  ломалась только на живом прайсе: терялись законные варианты, «(комплексное)» считалось
  пакетом, LLM не видела ответа правил, разметка каждой строки стоила 6–7 с. Сначала —
  свип по живым данным с разбором изменений, потом — проектирование под него.
- **Свип на `asyncio.run` для каждого вопроса ронял вызовы LLM** (клиент ollama привязан к
  циклу событий) — fail-open превращал это в «без изменений», и свип врал зелёным. Один
  цикл событий на весь прогон; в сводке — число сбоев LLM.
- **Подделка в тесте была dict, а настоящий тип — `ollama.Options`.** Тест был зелёным,
  живой вызов — TypeError. Подделки — того же типа, что настоящие объекты.
- **Свип скачал прайс 01.10 — и гейт покраснел** (он берёт последний срез на диске).
  После живых прогонов проверять гейт на том срезе, на котором он был зелёным, и отдельно
  — на новом.
- **Добавил к гейту `--timeout=600`** — плагина в venv нет, pytest упал до сбора тестов,
  обёртка сказала «exit 0». Гейт — только привычной командой, без новых флагов.
- **Офлайн-свип после самарской полуночи** без прикрепления срезов полез бы качать прайс
  и справочник «на сегодня» (и молча опустошил бы словарь синонимов). Свипы 02.10 —
  через прикрепление ОБОИХ срезов к последним на диске, сеть закрыта, размер словаря
  печатается (797 синонимов на срезе 01.10).

## 7. Предложение: метрики «до/после» (в духе RAGAS)

Владелец 01.10: «не могу однозначно сказать, `llm_price_service_select` — шаг вперёд или
назад; нужны метрики до/после». Сейчас есть только встречные свипы, размеченные
разработчиком (раздел 2, журнал SURGEON-PRICE): 45 вопросов через весь конвейер — 12
изменений, все исправления; 123 обрывка названий — 90 изменений, 2 потери законного
варианта. Это не независимая оценка.

- **Эталон.** 150–200 настоящих вопросов о цене из логов прода (`scripts/analyze_daily_dialogs.py`
  уже разбирает лог агрегатора); к каждому — какие строки прайса верны (код МИС, может
  быть несколько). Размечать только вопросы, где «правила» и «правила + LLM» ответили
  по-разному, плюс случайные 30 совпавших — это ~2–3 часа человека. В логах ПДн —
  набор хранить ВНЕ публичного репо.
- **Метрики для цены** (каждая — для обоих режимов):
  1. «чужая цена» — доля ответов, где показана хоть одна строка ДРУГОЙ услуги (главная:
     дезинформация ценой хуже уточнения);
  2. точность — верная строка есть среди показанных;
  3. полнота вариантов — какая доля верных строк показана (не потеряли 3 000 / 4 500 /
     10 000);
  4. «не нашёл» / оператор — цена осторожности;
  5. время ответа p50/p95 и число сбоев LLM (сработал запасной путь).
  В терминах RAGAS: 1 — context precision (нет ли чужого), 3 — context recall (ничего не
  потеряли), 2 — hit rate. Faithfulness (ответ не говорит того, чего нет в источнике) —
  для подготовки, где бот пишет текст сам.
- **Метрики для подготовки** (40–60 вопросов «как подготовиться к X» с эталонным
  источником): нашёлся ли нужный документ; есть ли в ответе строки из документа ДРУГОЙ
  процедуры (класс «Фортранса» — проверяется автоматически по совпадению строк); каждая
  ли рекомендация есть в источнике. Судья-LLM — только сильная модель офлайн: локальная
  mistral-small как судья слаба.
- **Как запускать:** один офлайн-скрипт на прикреплённых срезах (без прода и пациентов) →
  таблица «было / стало»; перед каждым деплоем, который трогает цену или подготовку.
  Оценка работ: скрипт — около дня, разметка — 2–3 часа.

**Решение владельца 02.10:** метрики — ПОСЛЕ деплоя кнопочной версии и связки шлюза с
ботом. До того готовность проверяем сами: журнал багов вживую + актуальность eval.
