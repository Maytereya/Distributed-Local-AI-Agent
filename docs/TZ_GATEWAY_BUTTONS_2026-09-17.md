# ТЗ для команды шлюза: кнопки в Telegram/WhatsApp

**Клиника «Наука», Самара · 17 сентября 2026 · для разработчиков мессенджер-шлюза**

Документ описывает ТОЛЬКО работы на стороне шлюза. Распознавание, цены, корзина
и тексты ответов — на стороне бота и в это ТЗ не входят.

---

## 1. Зачем

Сегодня пациент пишет свободным текстом, и бот угадывает, о чём вопрос. Замер по
живым обращениям: из девяти корзин анализов **ни одна** не дошла до нужной ветки
обработки — все потерялись на этапе «угадать намерение».

Кнопка убирает угадывание: намерение задано нажатием. Это самый дешёвый способ
закрыть самый частый отказ.

---

## 2. Главное требование, без которого работа теряет смысл

> **Нажатие кнопки обязано приходить в бота ИДЕНТИФИКАТОРОМ, а не текстом.**

Если шлюз при нажатии «Сколько стоит» отправит боту строку `"Сколько стоит"`,
бот снова окажется в положении «угадай, что имел в виду пациент», и весь эффект
кнопок пропадёт.

Нажатие передаётся в поле `button_id`. Поле `text` при этом либо пустое, либо
несёт подпись кнопки для истории диалога — но решение принимается по `button_id`.

---

## 3. Изменения в контракте API

Эндпоинты остаются прежними: `POST /api/messenger-generate` (стрим NDJSON) и
`POST /api/messenger-generate-once`.

### 3.1 Запрос — добавляется одно поле

```jsonc
{
  "session_id": "tg_123456789",   // как и раньше
  "text": "",                     // пусто при нажатии кнопки
  "button_id": "menu.price.calculator",   // НОВОЕ
  "llm_mode": "hybrid"
}
```

- `button_id` — строка-идентификатор из ответа бота. Шлюз **не придумывает** их
  сам и **не изменяет**: возвращает ровно то, что прислал бот.
- Одновременно `text` и `button_id` допустимы (пациент нажал кнопку и дописал
  текст) — бот разберётся.
- Если `button_id` неизвестен боту (устарел после перезапуска), бот ответит
  обычным текстом и покажет меню заново. Ошибкой это не считается.

### 3.2 Ответ — добавляется одно поле

```jsonc
{
  "text": "Что вас интересует?",
  "attachments": [],
  "handoff": false,
  "buttons": [                                  // НОВОЕ
    {"id": "menu.appointment", "title": "Записаться к врачу"},
    {"id": "menu.labs",        "title": "Сдать анализы"},
    {"id": "menu.results",     "title": "Результаты анализов"},
    {"id": "menu.price",       "title": "Сколько стоит"},
    {"id": "menu.address",     "title": "Адреса и часы работы"},
    {"id": "menu.docs",        "title": "Справки и документы"},
    {"id": "operator",         "title": "Оператор"}
  ],
  "state_update": {}
}
```

- `buttons` может отсутствовать или быть пустым — тогда шлюз ничего не рисует.
- Порядок кнопок сохранять как пришёл.
- `title` показывать дословно. Не переводить, не сокращать, не добавлять эмодзи
  от себя.
- В стриме (NDJSON) `buttons` приходит в **последней** строке ответа. Промежуточные
  строки кнопок не несут.

### 3.3 Что НЕ меняется

`session_id`, `text`, `debug`, `llm_mode`, `attachments`, `handoff`,
`state_update` работают как сейчас. Старые клиенты, не знающие про `buttons`,
продолжают работать — поле необязательное.

---

## 4. Меню

Шесть кнопок первого уровня плюс «Оператор», доступный всегда и на любом шаге.

| id | подпись |
|---|---|
| `menu.appointment` | Записаться к врачу |
| `menu.labs` | Сдать анализы |
| `menu.results` | Результаты анализов |
| `menu.price` | Сколько стоит |
| `menu.address` | Адреса и часы работы |
| `menu.docs` | Справки и документы |
| `operator` | Оператор |

Второй уровень бот присылает сам в поле `buttons` — шлюзу не нужно знать его
состав заранее. Для калькулятора он такой:

| id | подпись |
|---|---|
| `menu.price.service` | Цена анализа |
| `menu.price.doctor` | Цена приёма врача |
| `menu.price.promo` | Акции и скидки |
| `menu.price.calculator` | Пришлю список — посчитайте |
| `menu.back` | Назад |

---

## 5. Сценарий калькулятора

```
Пациент: [Сколько стоит] → [Пришлю список — посчитайте]
Бот:     «Пришлите список анализов — по одному в строке или через запятую.»
Пациент: ферритин, глюкоза, ТТГ        ← обычный текст, кнопок нет
Бот:     расчёт + кнопки [Убрать позицию] [Добавить ещё] [Всё верно]
Пациент: [Всё верно]
Бот:     handoff = true + cart в state_update
Шлюз:    передаёт оператору карточку с составом расчёта
```

Кнопки шага правки:

| id | подпись |
|---|---|
| `cart.remove` | Убрать позицию |
| `cart.add` | Добавить ещё |
| `cart.confirm` | Всё верно |

При `cart.remove` бот пришлёт кнопки по числу позиций
(`cart.remove.1`, `cart.remove.2`, …) — шлюз опять же просто рисует то, что пришло.

---

## 6. Передача расчёта оператору

Когда пациент подтверждает корзину, бот отвечает с `handoff: true` и кладёт
состав в `state_update.cart`:

```jsonc
"state_update": {
  "cart": {
    "items": [
      {"service_id": 507, "name": "Липидограмма", "cost": 860},
      {"service_id": 528, "name": "Глюкоза", "cost": 190}
    ],
    "taking":     {"service_id": 41, "name": "Взятие крови из вены", "cost": 195},
    "total_preliminary": 1245,
    "unrecognized": ["ГГТП"]
  }
}
```

**Что делает шлюз:** показывает оператору карточку с этим составом и суммой,
помеченной как предварительная, и списком нераспознанного.

**Что шлюз НЕ делает:** не пересчитывает сумму, не дополняет состав, не
обращается в МИС. Обязывающее коммерческое предложение оператор формирует своим
инструментом.

`service_id` — это идентификаторы позиций прайса МИС: по ним оператор соберёт
предложение в один шаг, не набирая названия руками.

---

## 7. Сессия

- `session_id` должен быть **стабильным** для одного чата: контекст живёт в нём.
  Смена `session_id` = новый пациент с нуля.
- Память сессии живёт **один час** и не переживает перезапуск бота. Если пациент
  вернулся позже, бот начнёт с меню — это ожидаемо.
- Нажатие кнопки — такой же ход диалога, как сообщение: его тоже надо слать с тем
  же `session_id`.

---

## 8. Telegram и WhatsApp

**Telegram.** Inline-кнопки под сообщением. При нажатии — `answerCallbackQuery`,
чтобы у пациента не висели часы, и затем запрос к боту с `button_id`.
Рекомендуется убирать клавиатуру у прошлого сообщения, чтобы пациент не нажимал
кнопки из середины диалога.

**WhatsApp.** Ограничение платформы: до трёх кнопок в сообщении, либо список
(list message) до десяти пунктов. Меню из семи пунктов рисовать списком.
Если платформа кнопки не поддерживает — показывать нумерованный текст, а ответ
пациента «2» превращать в соответствующий `button_id` **на стороне шлюза**.
Боту цифру пересылать нельзя: он поймёт её как название услуги.

---

## 9. Что в это ТЗ не входит

- Распознавание списка анализов, цены, развилки, тексты ответов — сторона бота.
- Формирование коммерческого предложения — инструмент оператора.
- Отчёт по обращениям — отдельная работа, к кнопкам не относится.

---

## 10. Критерии приёмки

1. Нажатие любой кнопки приходит в бота как `button_id`, идентичный присланному.
2. Кнопки из ответа бота отрисовываются в том же порядке и с теми же подписями.
3. Ответ без поля `buttons` не ломает клиента.
4. Неизвестный `button_id` не приводит к ошибке — бот отвечает текстом.
5. `session_id` стабилен в пределах чата и не меняется при нажатии кнопки.
6. При `handoff: true` с `state_update.cart` оператор видит состав, предварительную
   сумму и список нераспознанного.
7. В WhatsApp выбор пунктом списка даёт тот же `button_id`, что кнопка в Telegram.

---

## 11. Порядок внедрения

Поле `buttons` бот начнёт присылать только после согласования этого документа.
До тех пор шлюз может реализовать приём `button_id` — он безвреден для текущего
поведения, потому что бот игнорирует неизвестные поля запроса.

Разумный порядок: сначала `button_id` и меню первого уровня, затем второй
уровень, затем корзина с передачей оператору.
