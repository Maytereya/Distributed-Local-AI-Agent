### BUG-D «Срок готовности» анализа — ЕСТЬ ЛИ ДАННЫЕ В API? (вопрос владельца)
Д188: пациент спрашивает срок готовности ХМС по Осипову. **Сначала проверить, есть ли поле срока
готовности/`deadline`/`days` в прод-API** (`api_price` priceByRegion / каталог услуг). Если есть —
транслировать пациентам (новая фича в lab_tests/prices). Если нет — честный ответ «уточните в клинике».
→ Это исследование API на проде, потом решение.
**ОТВЕТ (09.06, по локальному кэшу каталога):** поле **`deadline` ЕСТЬ** в `priceByRegion` (формат строковый,
неоднородный: `"6-8"`, `"1-2"`, `"7-10"`, `"5-8 дн"`, `"до 7 дней"`, `"до 14"`, `"13"`, `"До 30 дней"`).
→ данные есть → фича реальна. Нюанс: формат **свободный текст** (дни/диапазоны/«до N»), не число — транслировать
**как есть** (буквально из `deadline`, как цены), без парсинга/нормализации в число. Решение по UX — за владельцем.
**✅ ФИКС (09.06, `39a81ee`, BUG-2026-06-09-03):** корень был не в данных, а в матчинге — «срок готовности ОАК»
не извлекал `test_name`, turnaround-шум ломал матч → `test_assist` отдавал «no matches». `strip_readiness_phrasing`
снимает фразу срока перед матчингом → анализ находится, `deadline` (уже в payload + промпт уже инструктирует) доходит
до пациента. Покрыто класс-инвариант + e2e тестами. **Прод-проверка после деплоя:** «срок готовности ОАК» → срок «1-2 дня».
Открыто (UX, за владельцем): гарантировать детерминированный вынос срока (сейчас LLM-путь) + readiness в мульти-айтем-запросе.
