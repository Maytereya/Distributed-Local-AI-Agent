## Анализатор: текущий допуск

Модель: `mistral-small3.2:24b-instruct-2506-fp16`,
фиксированный endpoint `http://ollama:11434/api/chat`.
Передаются только связанные с новым обращением сообщения: до 15 пациентских
и 15 ответов бота, по 500 символов. Переписка считается недоверенными данными;
модели не предоставляются инструменты. Выход — причина, действие и самооценка
уверенности из закрытых словарей. Свободное медицинское заключение / команда
не исполняются. Ошибка локальной модели не вызывает внешний fallback.

Подтверждённые событиями причины определяются правилами; ИИ-вывод помечается
как предварительный. Его уверенность не является вероятностью правильности.
`/failures [период]` показывает текущее состояние обращений, поступивших
в выбранный период. Исторический счётчик восстанавливает исход на конец
периода, поэтому его выборка не обязана совпадать с текущим разбором.
Возвращается до 100 карточек, не более двух новых модельных разборов за вызов.
`/failure [номер]` показывает типы задач, числа событий, основание причины
и предлагаемое действие. Тексты остаются в панели операторов.
В установленной версии прямой переход из аналитического номера в карточку
панели ещё отсутствует.

В дополнительном локальном пакете от 10.10 этот переход реализован:
карточка `/reporting/appeals/<id>/` требует действующего активного оператора,
показывает связанные оригиналы и время событий. HTML экранируется; нет
кеширования, внешних ресурсов или Referer. Убрана зависимость CSS от CDN
в пользу закреплённого Pico 2.1.1. Ручные оценки отделены от бизнес-счётчиков
и флагов допуска, устаревают при изменении доказательств. **На сервере эти

проверка `/api/ps`, только уже загруженная выбранная модель, использование

## Остаточные риски и дальнейшие проверки

1. **Внутренний клинический HTTP.** Действующий источник использует HTTP
   внутри сети клиники. Allowlist ограничивает получателя, но не шифрует
   трафик. HTTPS / защищённый транспорт требует настройки и проверки
   соответствующего клинического сервиса.
   Существующая панель оператора также доступна по внутреннему HTTP
   через VPN. VPN ограничивает маршрут, но не заменяет HTTPS браузерной
   сессии. Переход на TLS для панели / безопасные cookies требует отдельной
   настройки адреса и сертификата; дополнительные карточки не открывают
   новый публичный порт и наследуют действующий способ входа.
2. **Gradio 5.49.1.** Роли усилены, зависимость до новой основной версии
   не обновлена. Есть advisories для старых версий: `gr.load`/OAuth и Audio
   cache. В проверенном интерфейсе конкретные уязвимые пути не используются;
   отдельное обновление с проверкой совместимости и аудит зависимостей нужны.
3. **Разрешённая передача наружу.** Telegram получает пациентскую переписку
   и документы, клинические серверы — необходимые запросы. Сетевые запреты
   не означают отсутствия любой передачи за пределы сервера и не исключают
   компрометацию разрешённого получателя.
4. **Объём аудита.** Не выполнены полный pentest всех маршрутов, запись всего
   трафика, проверка всех форматов вложений и всего корпуса prompt injection,
   перезагрузка хоста, полноценная приёмка всех старых личных команд.
   Проверены конкретные механизмы и сценарии из этого документа.
5. **Хранение.** Старые логи, переписка и резервные копии автоматически
   не удалялись; действующие доверенные администраторы сервера сохраняют
   доступ. Срок хранения новых событий и копий требуется утвердить отдельно.
6. **Будущая рассылка.** Первые новые дневные отчёты назначены на 10.10.2026
   в 19:00 и 19:10 по Самаре. Расписание, окна, outbox и обработчики проверены;
   receipt именно этих будущих сообщений пока отсутствует.

Аппаратный отчёт показывает системный раздел и SMART обнаруженных NVMe.
Инвентаризация всех остальных файловых систем и их привязка к накопителям
не выполнялась. Пороги температур/нагрузки и автоматические аппаратные реакции
не утверждены; критический сигнал SMART производителя отображается как CRIT.

Старую небезопасную очередь отчётов автоматически не подключать.

Compose override установлен рядом с действующими Compose-файлами.
ID запущенных образов, итоговый аудит, снимки проверок и отчётов хранятся
на сервере в `/home/vl/.reporting-deploy/security-r4/final` (0700).
Значения секретов в экспортируемые доказательства не включены.

Дополнительный локальный пакет проверен 83 Python- и 8 Node-тестами
(включая 29 Django). Проверена согласованность `reporting.0004` с моделями;
его новые тесты ещё не выполнялись в серверном PostgreSQL/образе.
Порядок приёмки — [здесь](reporting_acceptance_2026-10-10.md).
Свежий дамп перед `reporting.0004` расположен в
`/home/vl/.reporting-deploy/review-r4/backup/pre-review.dump` (0600), SHA
сохранён рядом. Восстановление успешно. Временный `reporting-review-postgres`
на tmpfs без портов / во внутренней сети пока не удалось удалить из-за
потери связи; очистка — первый шаг следующего сеанса. Затем для тестов
создать чистую синтетическую БД. Рабочая база не изменена.
Сверка и безопасное объединение репозиториев —
[здесь](reporting_github_reconciliation_2026-10-10.md).

При внедрении были короткие перерывы компонентов. Исправлены права
API-ключа для root-процессов без capabilities. Затем проверка всех runtime UID
обнаружила несовместимость root/0400 с агрегатором; окончательные права ниже. Исправлена блокировка
PostgreSQL. До включения учёта обработаны три зависших turn уже переданных /
операторских диалогов; новых передач и повторных Telegram-отправок эта
операция не делала. Пропуски мониторинга сохранены как пропуски.
Ollama и загруженную рабочую модель не перезапускали.

**Проверка и исправление 10.10 после восстановления связи.** Web и poller
работают как UID/GID 1000, API — UID/GID 0. Общий root:root/0400-файл
действительно был недоступен агрегатору. Для текущих ролей установлен
root:1000/0440 в закрытом каталоге, readonly mount сохранён. Ключ не
печатали и не переносили с сервера. Все три процесса подтвердили чтение;
синтетический запрос из штатного клиента poller получил HTTP 200,
непустой ответ, handoff=false. Перезапусков для исправления не было.
Ошибка могла приводить к fallback/передаче вместо ответов; отсутствие
потерянных или затронутых обращений этой проверкой не доказано.
Перед дальнейшими изменениями UID/GID/mount использовать
[проверку](../openclaw/deploy/check_messenger_key_access.sh) и запрос самого
клиента агрегатора. Один успешный root-запрос к API недостаточен.

В ветке private_agregator исправлено также закрытие PostgreSQL-соединения
анализатором внутри транзакции вызывающего кода. На изолированном PG16,
с настоящими миграциями, пройдены 29 тестов журнала/панели/кеша и пять
проверок прав HTTP/WS/Telegram. Новая версия пока не выложена в live.
