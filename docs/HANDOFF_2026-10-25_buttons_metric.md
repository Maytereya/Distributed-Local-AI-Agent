# Метрика «рабочий бот»: успех внутри меню-кнопок — набор, критерии, первый замер (25.10)

Сессия wb-metric, ветка `claude/wb-metric-1be760`. Решение владельца 25.10: ~90% пациентов идут через меню-кнопки шлюза,
главная метрика — процент успешных ответов при живой LLM внутри кнопок, цель — 100%. В документе только счётчики и id
вопросов эталона; реплики пациентов, ответы бота и разметка — в `~/Dev/dla-private/bench/` (вне репо).

## 1. Как идёт ход в кнопке и что поменялось в стенде

Поток шлюза — два хода одной сессии: нажатие листа (`button_id` + подпись кнопки в `text`, «Таблица экранов, версия 1»),
затем вопрос пациента свободным текстом без `button_id`. Кнопка `slot` текст запроса не читает (тема и сущности —
из кнопки, `orchestrator._button_decision`), поэтому прежний режим стенда «кнопка и вопрос одним запросом» отдавал
подсказку кнопки и вопрос не проверял вовсе. Теперь вопрос набора с `press: true` идёт двумя ходами (`evalbench/run.py`,
коммит `affca04`); исход — по второму ходу, нажатие — в поле `press`; после кнопки-перевода второго хода нет.

- `~/Dev/dla-private/bench/sets/buttons_v1.jsonl` — 1008 вопросов эталона (`golden_v1` 868 + случайный слой 200) с листом,

  `labels/button_leaf/owner_sample_30.md` (18 спорных первыми). 284 судимых вопроса — `fit = nearest`: точного листа нет.

## 3. Критерий успеха

Успех = `success` (решено ботом по данным мира) + `handoff_ok` (честный перевод, где данных у бота нет по дизайну:
существующая запись, ДМС, дети, срок готовности, медсовет). Провал — с классом (`evalbench/buttons.py::FAIL_CLASSES`).

- **Цена** (листы цены) — без судьи, по разметке допустимых serviceId (`labels/price_allowed.jsonl`): успех — `correct` /
  `list_hit`, услуга не из прайса — ответ без цены. Цена приёма строкой врача — судья.
- **Сбой, служебный текст** — провал без судьи.
- **Остальное** — судья-LLM по ответу и данным мира (`buttons.JUDGE_INSTRUCTIONS`: критерий по каждой теме — адрес и часы
  по филиалам, памятка нужной услуги, верная инструкция по результатам, запись к нужной специальности, нужные врачи);
  вердикт привязан к (id, отпечаток ответа) — неизменный ответ второй раз не судится.
- **Надёжность судьи:** скептик вслепую на 60 вердиктах (20 провалов, 20 переводов, 20 успехов) согласен в 53 (88%);
  все 7 расхождений — скептик строже (филиал без анализов в списке, перевод при данных в мире). Значит, 63% — оценка
  сверху; по выборке скептика ниже на ~4–7 п. п. Выборка 30 вердиктов владельцу — `labels/button_judge_owner_sample_30.md`.

## 6. План до 100%

Порядок — по вкладу и по тому, где уже идёт работа. Каждый шаг — LLM-first, под выключателем, карточка на `buttons_v1`
против `wbm_d18`; правило ≤3 и чужая цена — как раньше. Набор — мерило: под его вопросы не подгонять.

1. **A — запись, ответ на вопрос кнопки — СДЕЛАНО под `booking_target_slot_llm` (off).** Вопрос цели записи стал вопросом-слотом
   одной функции (`pending_answer`); карточка `bkt_on4` против `wbm_d18`: вопрос об отмене 30 → 0, лист записи 52% → 64%, в целом
   63% → 64% (570 из 886), хуже 0. Класс E (ДМС, дети, онлайн → оффер оператора, как текстом) — там же (`8563589`): `bkt_on6` —
   65% (579 из 886), лист записи 72%, против `wbm_d18` хуже 1. Включение — решение владельца. BUG-2026-10-25-BOOK-BUTTON-REPLY-AS-TOPIC-SWITCH.
2. **C — цена внутри кнопки (10,3 п. п.).** Сессия «максимум из кнопок»: внутри ценовой кнопки не уходить в чужую тему
   (подбор, филиалы), не повторять подсказку кнопки, список вариантов с ценами вместо «на какую услугу вас записать».
   Сужение поиска кнопкой второго уровня не должно отрезать УЗИ и процедуры: «Цена анализа» — ближайший лист для всех
   не-приёмов (ТЗ: 29% ценовых диалогов — приёмы, УЗИ, процедуры). Цена приёма с вариантами — список (7 вопросов).
3. **B — вопрос внутри кнопки-адреса (9,8 п. п.).** Второй ход после `menu.address` / `menu.tests.where` — ответ на
   конкретику по данным филиалов (названный филиал, выходные, флаги `analysis` / `usi` / `ecg`); чего в данных нет
   (праздники, услуга в конкретном филиале) — честно и оператор. Фильтр `analysis` в списке «где сдать» — дефект данных,
   отдельный быстрый фикс. BUG-2026-10-25-PASS-BUTTON-FOLLOWUP-BRANCH-TEMPLATE.
4. **E, F, D, H — по темам (≈13 п. п.):** ДМС / дети / онлайн в ответе на вопрос записи → оператор (так бот уже отвечает на набранный текст);
   конкретный вопрос о результатах — ответ, не шаблон; акции — «такой акции нет» вместо общего списка; подбор анализов —
   комплексы и чекапы из прайса.
5. **Пробелы меню (решение владельца):** вопросы без точного листа дают 44% успеха против 71%. Кандидаты — «где делают
   услугу» (отложено до конца рефакторинга), цена процедуры / УЗИ, правила приёма биоматериала (возраст, время).
6. **Прибор:** выборки владельцу (лист — 30, судья — 30) — после ответа поправить разметку (`fix_*.jsonl`) и судью;
   судить строже по пунктам скептика; второй вход в цену (`menu.tests.price`) и соседний лист (`alt`) — замер устойчивости.

## 7. Как мерить другим сессиям

Заметка `wb-metric_buttons_set_2026-10-25.md` в общей папке заметок: команда прогона и карточки, судья для изменившихся
ответов (`python -m evalbench.buttons judge-export`), замок живой LLM. База для сравнения — `wbm_d18`.

## 8. Решения на проверку владельцем

- Разметка листа: 30 вопросов (`owner_sample_30.md`), особенно спорные — «есть ли услуга в филиале» (поставлено «Адреса»),
  справки на осмотр (поставлено «Цена анализа»), запись на чекап (поставлено «Нужно ли записываться»).
- Судья: 30 вердиктов (`button_judge_owner_sample_30.md`); главный вопрос — засчитывать ли успехом общий список филиалов
  с часами, когда спросили про один филиал или выходные (сейчас — провал «шаблон вместо ответа»).
- Честный перевод входит в успех (иначе 100% недостижимы по дизайну: существующая запись, ДМС, срок готовности).
