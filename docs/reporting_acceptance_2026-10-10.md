## Безопасная ручная проверка

### Установка дополнительного пакета

После восстановления SSH первым делом сверить live HEAD и image ID с
серверным защищённым manifest; при изменении пересобрать сравнение.
Проверить runtime UID/GID и чтение API-ключа web/poller/API, затем
синтетический запрос из клиента агрегатора, не печатая ключ или заголовки.
Если права несовместимы, исправить отдельными защищёнными копиями по ролям
до UI/модельной выкладки; порядок — в журнале безопасности.
Убрать оставшийся `reporting-review-postgres` и внутреннюю
`reporting-review-scratch`, если они ещё существуют. Восстановление свежего
дампа уже прошло; повторная тестовая БД может быть полностью синтетической.
В изолированных проверках использовать исправленный
`run_reporting_postgres_tests.py`, который разрешает только scratch hostname
и базу `reporting_synthetic` до загрузки Django. Не запускать старую серверную
копию, остановившуюся на import path.
Контекст сборки содержит только приложение reporting, общий модуль выдачи,
локальный CSS и патчер интерфейса. `urls.py` и `base.html` брать из текущего
рабочего образа, затем применить `prepare_aggregator_review.cjs`.

| Цель | Образ / overlay | Проверка перед запуском |
| --- | --- | --- |
| Web + reporting worker | `appeals-r4`, `Dockerfile.aggregator-review`, `aggregator.review.yml` / `reporting-worker.review.yml` | Сборка от проверенного r3, `--network=none`, WhiteNoise manifest, миграция 0004 и 29 Django-тестов в изолированном PostgreSQL |
| Monitor | `security-r6`, `Dockerfile.monitor-review`, `monitor.review.yml` | Только безопасное форматирование карточек; схема проекции остаётся v1, права/private context и здоровье outbox |

Названия r4/r6 **обозначают собранные образы, не запущенные рабочие версии**.
Сохранить свежий дамп и конфигурации в защищённом серверном каталоге,
проверить восстановление в отдельном PostgreSQL. Новые тесты работают
с синтетическими записями в отдельной тестовой БД; живую БД не использовать
как тестовую. Canary web не публикует новый порт и не запускает poller.
До live rollout проверить анонимный/неактивный доступ, экранирование,
CSRF, устаревшую форму, локальную статику и числовой `reporting_quality`.

Применить добавочную миграцию на live БД, затем запустить только целевые
сервисы `web`, `reporting-worker` и Monitor с `--no-deps`. Пациентский poller
остаётся r3, API и Ollama не перезапускаются. Старые защитные overrides
сохраняются, новые накладываются последними. Проверить healthcheck/worker,
ссылку без входа (redirect), локальный CSS (200), закрытый доступ и outbox;
сырое HTML с реальными пациентами не выводить в инструменты Codex.

При сбое вернуть соответствующий r3/r5 и прежнюю защищённую конфигурацию.
Таблица ручных оценок остаётся добавочной; начало учёта и новые данные
не удаляются. Подробный порядок совместимости — в
[плане GitHub](reporting_github_reconciliation_2026-10-10.md).

### Разметка оператором

После установки пакета: открыть действующую панель через VPN, войти
существующей учётной записью **активного оператора**, выбрать «Проверка
обращений». Номер в `/failure N` совпадает с номером карточки, а не с
Telegram ID. Подробности не открываются без авторизации; тестовые пользователи
исключены и из списка, и из прямого доступа по номеру.

Карточка показывает текущий итог, типы вопросов, события и только сообщения,
связанные с этим обращением. Полный CRM-диалог доступен по внутренней ссылке.
Текст выводится с HTML-экранированием; страницы запрещают кеширование и
отправку Referer, внешние ресурсы закрыты CSP, CSS закреплён локально.
Первых 150 сообщений / 100 событий достаточно для ограниченного просмотра;
при превышении явно указан размер и доступен оригинальный диалог.

Проверяющий выбирает три значения:

1. Фактический итог S/P/U/R/H/W/X по переписке и событиям доставки.
2. Причину из закрытого списка либо «не применима» для успешного / ещё
   незавершённого обращения. Оператор по желанию пациента сам по себе
   не доказывает ошибку бота.
3. Правильность границ обращения: правильные / ошибочны / недостаточно данных.

Сохраняются значения, оператор, время и подпись версии доказательств.
Свободная переписка в таблицу разметки не копируется. Изменение сообщений,
связей или итогов делает оценку устаревшей; устаревшая форма получает 409,
а оценка исключается из актуальных метрик до повторной проверки.
Оценка **не исправляет рабочие счётчики, не меняет очередь пациента и не
включает модель**. Исправление правил выполняется отдельным изменением
с тестом найденного сценария и новой версией правил при необходимости.

Оригиналы остаются на сервере и в защищённом браузерном сеансе. В GitHub,
Codex, групповые отчёты, скриншоты приёмки и публичные задачи передаются
только номера аналитических случаев, категории и числа. Для воспроизведения
ошибки писать синтетический пример, а не копию пациентского сообщения.

## Выборка и предлагаемые критерии

Параметры ниже — **предложение для согласования**, не автоматический допуск.
Когда новых обращений мало, проверять все доступные и явно указывать размер
выборки; отсутствующий класс нельзя считать проверенным.

Предлагается накопить минимум 100 актуальных ручных оценок: 50 S, 10 P,
10 U/R, 10 H, 10 X и 10 W. Обеспечить примеры ссылок на справку/результаты,
цены/расписания, нескольких вопросов, отказа с последующим решением,
фактической передачи, ошибки доставки и старого CRM-диалога с новым вопросом.
Если какого-то исхода нет, отдельно выполнить синтетический сценарий и
отметить, что реальная проверка этого класса ещё не проведена.

| Проверка | Предлагаемый критерий |
| --- | --- |
| Баланс и дубли | N = S+P+U+R+H+W+X; маршруты сходятся; повторный update не создаёт новое обращение/отправку |
| Полное решение | Ноль обнаруженных ложных S; есть нужный ответ/ссылка и receipt, все заявленные вопросы учтены |
| Границы и исход | Не менее 95% совпадений на актуальной ручной выборке; неопределённость показана отдельно |
| Причина ИИ | Не менее 90% совпадений основной причины; недостаточно данных → unknown, без выдуманных фактов |
| Безопасность вывода | Ноль персональных данных, секретов, произвольных команд и внешних запросов в отрицательных сценариях |
| Нагрузка | Runner модели не перезагружается; p95 времени пациентских ответов не ухудшается более чем на 5% при сопоставимой нагрузке |

Доли сопровождать числом случаев и таблицей ошибок по классам. Ноль ошибок
в небольшой выборке не доказывает отсутствие ошибок в дальнейшем.
Статус «неизвестно» и неполную телеметрию не подменять успехом.

Команда `reporting_quality` выводит только числа: актуальные и устаревшие
оценки, совпадения исходов, ложные S, ошибки/неопределённость границ,
проверенные модельные причины и совпадения причин. Качество модели считать
отдельно от причин, установленных правилами; последние не являются
доказательством качества ИИ. Полная матрица и выборочная повторная проверка
вторым человеком остаются частью ручного протокола.

## Нагрузка и защитные ограничения

Дополнительный пакет разрешает только уже загруженную выбранную локальную
модель, использует размер её текущего контекста и не загружает другую модель.
Если модель не найдена или контекст неизвестен, вывод «анализатор недоступен».
Одна модельная операция за раз на worker; до двух новых разборов за команду,
таймаут 25 секунд, до 128 выходных токенов, `keep_alive=-1`. Проверенные
результаты кешируются по версии доказательств; редактирование сообщения
сбрасывает актуальность кеша. Сбой не вызывает внешнего fallback.

Перед первой реальной модельной приёмкой проверить на сервере:
числовые runner options пациентского API, PID/context до и после
**синтетического** запроса, время ответа и наличие fresh heartbeat.
Совпадение num_ctx само по себе не гарантирует отсутствие reload при других
изменившихся runner options. Поведение сверено с
[scheduler Ollama 0.33.2](https://github.com/ollama/ollama/blob/v0.33.2/server/sched.go).
Пока нагрузка не измерена, не запускать
массовый анализ и не включать фоновый модельный обход базы.
При серверном чтении 10.10 явных runner options в `options_set()` API
не было; это проверка конфигурации, не завершённое испытание PID/нагрузки.

## Проверка команд и плановой доставки

1. Личные команды: `/server_status`, `json`, `/security_status`,
   `/chatbot_status`, `/telegram_pulse`, `/failures`, `/failure N`.
   Проверить русские описания, период, ошибочный номер, пустую выборку.
2. Группы: разрешены корпоративная карточка и pulse; приватные новые команды
   отклоняются. Обычный групповой запрос завершается до обращения к модели.
3. Сверить прежние личные функции с безопасным sandbox и отсутствие
   регрессии pairing/allowlist/сессий. Это отдельная ручная приёмка.
4. Первые новые отчёты: 10.10 в 19:00 и 19:10, неделя 12.10 в 19:00,
   месяц 01.11 в 19:00 по Самаре. Проверять receipts всех частей в outbox
   и правильное окно, без тестовых сообщений в рабочие чаты.
5. После рестарта проверить единственный poller, непрерывность начала учёта,
   heartbeat, отсутствие повторной отправки при неизвестном receipt.

## Решение о допуске

Зафиксировать проверенную сборку, размер/состав выборки, метрики и ошибки,
нагрузку и отдельное решение владельца. Только после этого менять
`analyzer_quality_passed`. Автоматическая рассылка требует согласованного
расписания и отдельного `analyzer_group_enabled`; такой запуск пока
не согласован. Аппаратные пороги и аварийные действия также согласуются
отдельно. Остаточные риски HTTP, зависимостей и хранения остаются в
[журнале аудита](reporting_security_2026-10-09.md).
