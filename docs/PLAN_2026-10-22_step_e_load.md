## 2. Нагрузочный режим стенда — `evalbench.run --concurrency N`

N ходов разных сессий одновременно в одном процессе бота, через тот же эндпоинт. Время, ответ и исход — у каждого хода
свои; вызовы LLM по ходам не разнести (копятся на прогон) — в строке хода `llm_calls = null`, итог — `load_llm_outcomes`
в `run.json`.

**Офлайн (replay, LLM мгновенная), test 201, код `ae02b53`:**

| N | Время прогона | Ход p50 / p95 / max | PRICE p50 / p95 | Ответы ≠ последовательному |
|---|---|---|---|---|
| 1 | 48 с | 0,07 / 0,85 / 2,2 с | 0,48 / 1,07 с | 0 |
| 4 | 48 с | 0,21 / 3,4 / 6,2 с | 2,2 / 4,6 с | 0 |
| 8 | 50 с | 0,59 / 6,8 / 10,8 с | 4,9 / 8,3 с | 0 |

**Вывод:** путь бота вне LLM исполняется строго по очереди (≈ 4 хода в секунду при любом N — общий цикл событий
и GIL); одновременные пациенты ждут друг друга ещё до очереди к LLM. Состояние между сессиями не протекает (ответы те же).
Ёмкости по CPU с запасом (прод — единицы ходов в час), но всплеск из 4 одновременных ходов добавляет секунды к хвосту.
До E1/E2 то же было бы в 5–6 раз хуже.
