# Корзина-калькулятор: базовый объём ТЗ 17.08 §6 (25.10.2026)

Источники: ТЗ `docs/TZ_TOPIC_BUTTONS_AND_CALCULATOR_2026-08-17.md` (§6 и «ОТВЕТЫ ЗАКАЗЧИКА» 16.09), согласованная схема
калькулятора `docs/BUTTONS_SCHEME_2026-09-17.md` §5–§7, принципы `docs/ARCHITECTURE_PRINCIPLES.md` (п. 1–3, 5), решение владельца
22.07 «дезинформация ценой хуже уточнения», порядок владельца 25.10 (рабочий бот → корзина → деградация → безопасность).
Журнал — STEP-2026-10-25-BASKET-CALC.

## 1. Что видит пациент (под `[MESSENGER_ROUTER] basket_calc = on`)

```
По услуге «оак»:
1. Общий анализ крови (Le, Er, Hb, СОЭ) — 390 руб.
2. Общий анализ крови (полный)(…) — 550 руб.

По услуге «Ферритин»:
1. Ферритин — 530 руб.

По услуге «Глюкоза»:
1. Глюкоза — 190 руб.

Итого по прайсу: от 1 110 руб. до 1 270 руб. — зависит от варианта «оак». Чтобы посчитать точно, пришлите список с нужными вариантами.
Взятие биоматериала оплачивается отдельно:
— Взятие крови из вены — 195 руб.
Скидки применяет регистратор при оформлении.
```

Позиции — как раньше (корзина из фраз разбора или корзина правил, выбор строк LLM). Под ними — блок калькулятора; под off ответ
байт в байт прежний.

## 2. Решения

**Итог при развилке — диапазон, а не «сумма без позиции + вопрос».** Позиция с несколькими ценами после базового варианта —
развилка (решение 22.07: при неоднозначности — варианты, а не одна цена). Итог «от суммы меньших до суммы больших»:
- диапазон — правда: настоящая сумма в нём лежит; сумма без позиции занижает итог и читается как полная — это та самая
  дезинформация ценой;
- вопрос «какой вариант?» бот следующим ходом не примет: ожидания (`_expects`) для него нет, ответ «полный» ушёл бы в путь одной
  услуги (принцип 5 — бот знает, чего ждёт). Поэтому вместо вопроса — что прислать: список с нужными вариантами корзина посчитает.
Итог печатается от двух позиций с ценой; есть нераспознанные или без цены — «Итого по прайсу за найденные позиции».

**Сумма — по прайсу, скидки не входят** (схема §7: скидки не формализованы, их применяет регистратор; `/commercial-offer` тоже
складывает прайсовые цены — `docs/HANDOFF_2026-09-25.md`). Отсюда «Итого по прайсу» и «Скидки применяет регистратор при оформлении».

**Взятие — в перечне под итогом, не в сумме** (ответ заказчика 16.09: «более простой путь» — после суммы «Взятие биоматериала
оплачивается отдельно» и позиции взятия). Вопрос владельцу — §5 (а).

**Взятие — по данным.** Строки прайса взятия — как их назвал заказчик: «Взятие крови из вены», «Взятие крови из пальца»,
«Взятие мазка (соскоба)» (никогда «Взятие крови без последующего исследования»); цена — из прайса по названию. Какое взятие
нужно позиции:
1. «капиллярная» в названии строки прайса → из пальца (правило заказчика);
2. иначе — по материалам МИС (`biomatNames`): кровь → из вены (кровь из пальца / капиллярная — из пальца); соскоб, мазок → мазок;
3. `biomatNames` перечисляет ДОПУСТИМЫЕ материалы, а не выбранный: взятие выводится, если всем допустимым материалам, которые
   берут в клинике, нужно одно и то же; материалы без взятия (моча, сперма, пунктат) его не отменяют — перечень предупреждает о
   доплате, когда материал берут; у ОАК («кровь из вены, кровь капиллярная») — из вены;
4. взятие разное («кровь из вены, соскоб с шейки матки» у чекапа) или у развилки варианты требуют разного — из данных не выводится:
   остаётся одна оговорка «Взятие биоматериала оплачивается отдельно.» (заказчик: она закрывает невыводимое);
5. услуги нет в справочнике МИС — о взятии данных нет; взятие, которое пациент назвал сам, — позиция корзины, в перечень не входит.
Живой прайс 08.10 (3 671 строка): лабораторных строк со справочником — 1 205 из 1 238 (вне справочника — в основном Cito, их
базовый вариант и так снимает). Мини-прод (404 строки): из пальца 3, из вены 169, мазок 38, без взятия 166, оговорка 24.

**Базовый вариант** — `_prefer_base_variants` в `_basket_select._positions` (обе корзины): без cito, капиллярной, детского, на дому,
повторного, к.м.н., если пациент их не просил. Осталось больше одного — развилка (итог «от … до …»), не «самый дорогой»
механически (ТЗ: это систематически завышало бы цены). **Т3 / Т4 — свободные по данным клиники:** в `serviceSynonyms` среза 03.10
«Т3» → сТ3, «Т4» → сТ4 — сильное совпадение корзины берёт их без LLM; правило в коде не нужно.

**Цена 0 в прайсе — «не указана»:** если у любого показанного варианта цена 0, итог не печатается (сумма неизвестна). **Пациент
просил «из пальца», а показаны не капиллярные строки** — взятие из данных не выводится (только оговорка), чтобы перечень не спорил
с его словами. Оба класса нашёл судья набора кнопок (журнал, карточка).

## 3. Код

- `agent_logic_2/config.py` — ключ `basket_calc` (`MR_BASKET_CALC`, off).
- `messengers_router/services/_basket_select.py` — `basket_calculation` (итог по группам, как их печатает рендер; взятие —
  `_row_takes`), телеметрия хода `basket_total` (`single` / `exact` / `range`), `basket_takes`, `basket_take_unknown`.
- `messengers_router/services/_prices_helpers.py` — `multi_price_payload_from_items(..., calculation=)` → `payload["basket_calc"]`
  (+ `partial`).
- `messengers_router/services/prices.py` — `_multi_price_payload` передаёт расчёт (две строки; путь одной услуги не тронут).
- `messengers_router/renderer.py` — `_basket_calc_lines`; `messengers_router/text_templates.py` — тексты.
- `evalbench/prices.py`, `evalbench/card.py` — детектор знает итог (сходится с позициями — `total`, нет — «без источника») и
  перечень взятия (`take` — не услуга ответа); строки карточки.

## 4. Полный объём (не делается) — что нужно от клиники и шлюза

Полный объём ТЗ — «то же + передача расчёта оператору и файл предложения».
- **Шлюз:** (1) кнопка «Пришлю список — посчитайте» (меню «Сколько стоит») — лист и его `button_id` (сессия кнопок, заметка в
  общей папке); (2) кнопки правки корзины (схема §5, шаг 5: «Убрать позицию», «Добавить ещё», «Всё верно»); (3) **доставка
  подтверждённой корзины оператору** — канал и формат: оператор получает состав с `serviceId` строк прайса, не набирает
  названия руками; (4) отдача файла пациенту, если файл предложения шлёт бот, а не оператор.
- **Клиника / МИС:** (1) `POST /commercial-offer {"services": [serviceId…], "region": 3}` отдаёт PDF по прайсовым ценам (июль, сентябрь)
  — подтвердить, что метод не добавляет взятие сам (проверка 07.09: не добавляет) и что бот вправе звать его от имени пациента
  (учётные данные `/site/*`); (2) кто отвечает за предложение — оператор своим инструментом (схема §5, шаг 6) или бот файлом;
  (3) синонимы — данные клиники: «оак» в МИС — синоним трёх строк (полный 550, 390 и капиллярный 500), поэтому «оак» — развилка
  390/550; если базовым должен быть «полный» (ответ 16.09), клиника снимает синоним «оак» с остальных строк — без правки кода.
- **У нас после этого:** состояние корзины между ходами (сейчас корзина — один ход), ожидание ответа на «Всё верно» через одну
  функцию ответа на вопрос бота (`pending_answer`), сводка оператору (как Ш6 цены этапа 2), клиент `/commercial-offer` под выключателем.

## 5. Вопросы владельцу

- (а) Согласованная схема (§5, пример) кладёт «Взятие крови из вены — 195» в таблицу позиций и в сумму (1 875), а ответ заказчика
  16.09 допускает проще — сумма без взятия, под ней оговорка с перечнем. Сделано проще (бриф); «взятие в сумме» — одна правка
  рендера и расчёта, если нужно как в примере.
- (б) ОАК: базовым заказчик назвал «полный» (550), ТЗ запрещает «самый дорогой» механически — сейчас развилка 390/550 (§4, синонимы
  клиники).
- (в) Схема обещает на нераспознанное «Уточните название — добавлю в расчёт»; бот пишет «помогу по ним отдельно»: дописать в
  расчёт следующим ходом он не умеет (корзина — один ход). Обещание — после состояния корзины (§4).
