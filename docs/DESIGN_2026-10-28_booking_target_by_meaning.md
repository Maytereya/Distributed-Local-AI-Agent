# Цель записи по смыслу: что в реплике услуга, филиал и дата — размечает LLM, значения — данные (28.10)

Источник — аудит С6 (`~/Dev/handoffs/c6_rules_audit_2026-10-28.md`, разделы `flow_prelock` и `rule_appointment`; журнал
STEP-2026-10-28-C6-BRANCHES-TO-LLM) и аудит правил NLU 27.10 (группы «Цель записи по буквам», «Запись»). Направление владельца
27.10 — LLM-first: правило, которое отвечает раньше LLM и ошибается, уходит на решение LLM по замеру. Принципы: 2 (смысл — LLM,
выбор из перечисленного), 1 (факты — из данных), 5 (бот знает, чего ждёт). Выключатель `[MESSENGER_ROUTER] booking_target_llm =
off | on`, по умолчанию `off` — как было.

## 1. Класс дефекта

Поток записи берёт цель из первой содержательной реплики — на листе «Записаться на приём» это ответ на «К какому врачу или на
какую услугу записать?» (`flow_prelock`), в свободном тексте — ход с веткой `rule_appointment`. Реплику на роли режут регулярки:
кто услуга, кто филиал, кто дата. Стенд деплоя 19 (`s19all_*`):

| Реплика | Что вырезали буквы | Ответ |
|---|---|---|
| g0862 «Записаться на ФГДС на Ленина 5 — 8 октября» | филиал = «ФГДС» (первое «на …»), Ленина не прочитан | «Какой филиал вам удобен?» (К13) |
| g0393 «запись к терапевту на это воскресенье. Желательно на Ленина» | филиал не прочитан | снова филиал (К13) |
| g0474 «Запись на узи 2 скрининг» | услуга = «УЗИ», филиал = «узи 2» | «Да, можем записать на УЗИ (узи 2)» (К13, К8) |
| g0797 «Терапевт мне нужен на осетинской 4» | услуга = «Осетинской», филиал = «осетинской 4» (такого нет) | «Да, можем записать на Осетинской (осетинской 4)» — **дезинформация местом** (К8, S1) |
| g0730 «Уздг бцс ребёнку 8 лет» | филиал = вся реплика | «к какому врачу?» |
| g0556 «трансабдоминальное УЗИ в клинику на Финютина» | услуга = «УЗИ» | список всех УЗИ-филиалов |

Корень один: **роль слова решают буквы** (`extract_branch_hint` — «на <слово>» и «реплика до 6 слов», `extract_service_phrase` /
`_extract_service_keyword` — реплика без стоп-слов, `parse_date_time_ru` по всей реплике). Значения потом сверяются с данными
(каталог, роли, справочник филиалов), но на вход сверке уже попала чужая роль, а филиал без совпадения в справочнике пишется в
слот сырым текстом (`looks_like_branch_hint`).

Второй класс — тот же корень с другой стороны: когда тему записи решает LLM-классификатор (`rule_appointment` в `topic_by_llm`,
карточка С6: 20 лучше / 20 хуже), он заполняет `service_name` свободным текстом («Хочу записаться к врачу» → «врач»). Заземление
роняет неподтверждённую услугу, гард B′ отвечает «Пока не понял, к какому врачу… Перевести на оператора?», поток записи не
стартует. Свободный текст LLM — не выбор из перечисленного (принцип 2).

## 2. Что поток записи берёт у правил сейчас

| Сущность | Источник сейчас | Читатель |
|---|---|---|
| `appointment_action` (book / cancel / reschedule) | `detect_appointment_action` (буквы) — ветка `rule_appointment`; LLM-классификатор — если тема у LLM | `missing_slots`, пути отмены / переноса |
| цель: `service_name` | `_extract_service_keyword` (ветка правила), `extract_service_phrase` (`_fill_appointment_entities`) — реплика без стоп-слов | суд услуги `judge_booking_service` (LLM по каталогу) |
| цель: `specialty` | `extract_specialty` по всей реплике | роль `role_pick` (LLM по каталогу ролей МИС) |
| цель: `doctor_name` | `_extract_doctor_name` / `resolve_cached_doctor_name_candidate` + «контекст врача» регуляркой | проверка врача по справочнику |
| филиал `branch_id` / `branch_name` | `extract_branch_hint` (регулярки) → `match_branch_hint` по справочнику; нет совпадения — сырой текст | вопрос филиала, заявка |
| дата и время | `parse_date_time_ru` по всей реплике | заявка (`appointment_wish`) |

Специальность и услугу **по смыслу уже решает LLM** (`role_pick`, `judge_booking_service`) — но только среди того, что вырезали
буквы. Значит, менять нужно не судей, а разрез реплики на роли.

## 3. Решение: LLM размечает слова реплики по ролям, значения — данные

Как у цены (`turn_spans`, DESIGN-2026-10-23-NO-STOPWORDS): реплика показывается с номерами слов, LLM возвращает группы номеров и
метку действия — **выбор из перечисленного**, выдумать текст нельзя (фраза = подстрока реплики по построению).

Задача `booking_target` (своё место LLM, промпт `booking_target`, `generate_structured`, в бюджете решений хода):

```
{"action": "book" | "cancel" | "reschedule" | "none",
 "target": [[первое, последнее], ...],   // к кому или на что записаться: специальность, фамилия врача, услуга
 "branch": [[первое, последнее], ...],   // адрес или место филиала
 "date":   [[первое, последнее], ...]}   // дата и время
```

Проверка контракта (`judge`): номера 1..n, перечень по возрастанию (с пропуском — несколько групп), группы не пересекаются между
ролями; иначе `invalid`. «Врач», «приём»,
«процедура» без названия — не цель (правило промпта, как у разметки цены: общее слово — не услуга).

Значения — код по данным:

| Роль | Как получается значение | Нет совпадения в данных |
|---|---|---|
| `target` | слова группы — кандидат цели: `specialty` — `extract_specialty` по словам группы, врач — справочник врачей по словам группы, `service_name` — слова группы. Дальше — прежние судьи по смыслу: `role_pick`, `judge_booking_service`, проверка врача | судьи: «уточните услугу» / список вариантов / честный отказ, как сейчас |
| `branch` | `match_branch_hint` по справочнику филиалов (или по показанным вариантам) | **слот пуст** — бот спросит филиал списком по данным; сырой текст в слот не пишется (принцип 1: «Осетинской 4» не филиал) |
| `date` | `parse_date_time_ru` по словам группы (структурный разбор — правило остаётся) | даты нет — оператор подберёт время, как сейчас |
| `action` | метка LLM; **монотонно**: отмену или перенос, найденные правилом, LLM в «записаться» не превращает (как срочность — поднять может любой слой, снять — никто; отказ, понятый как согласие, запрещён принципом 5) | `none` — действие не меняется |

Цель, филиал и дата этого хода берутся **только** из разметки: прежние значения правил и свободный текст LLM-классификатора
(`service_name`, `specialty`, `doctor_name`, `branch_*`, `date_*`, `time_*`) из решения хода снимаются, быстрое дозаполнение
(`quick_fill_entities_from_text`) на этом ходу цель, филиал и дату по всей реплике не вырезает. Прочие слоты (ДМС / ОМС, город,
возраст ребёнка, ФИО по шагу ФИО) — как были. Врач, подтверждённый справочником до этого слоя (`doctor_name_verified`), остаётся.

Где что пишется: цель — в решение хода до роли и суда услуги (их решают `role_pick` и заземление, как раньше); филиал и дата —
дозаполнением того же хода из разметки (заземление ответа на вопрос цели принимает только слоты цели — так было и у разреза по
буквам). Предпроверка записи (`flow_prelock`) размечает реплику сама, до NLU, и держит запись, если разметка нашла хоть одну роль.
Нажатие кнопки (текст хода — подпись кнопки) не размечается.

Добавлено по замеру 28.10 (карточка и судья вслепую):
- **Значение цели на шаге цели — как у разреза.** Дозаполнение пишет цель из слов группы при тех же условиях, что разрез по
  буквам (`_fill_appointment_entities`): база держала слова пациента поверх сильного совпадения заземления, иначе общее «УЗИ»
  сводилось синонимом клиники к «УЗИ брюшной полости (комплексное)» («гинекологическое УЗИ» — тоже). Разметка меняет роли слов,
  а не судью услуги.
- **Слово специальности — приём, а не процедура.** Слова цели называют только роли приёма каталога ролей МИС («к терапевту»,
  «гинекологу») — `service_name` в решение не идёт, роль решает `role_pick` («гинекологу» иначе совпадало с «УЗИ гинекологическое»
  по синониму). Процедура в словах («гинекологическое УЗИ») — услуга.
- **Филиал, где цели нет по данным хода, в заявку не идёт (К8).** Разметка читает филиал чаще разреза, и открылся дефект «запись
  не сверяет услугу и филиал»: «трансабдоминальное УЗИ на Финютина» → «Да, можем записать… стоимость», а этого УЗИ там нет.
  Филиал сверяется с адресами цели (`ek.ADDRESS`); нет среди них — бот показывает филиалы, где цель есть. Адресов нет или врач
  выбран — как было.
- Перечень номеров с пропуском предлога («8 октября в 10» → `[7, 8, 10]`) — несколько сплошных групп, а не нарушение контракта.

## 4. На каких ходах

- Тема хода — APPOINTMENT (решило правило, LLM-классификатор или предпроверка записи `flow_prelock`), действие не
  отмена / перенос из прошлого хода.
- Цель записи ещё не известна: первый ход записи (поток не активен) или висящий вопрос записи ждёт цель
  (`_any_of:doctor_id,doctor_name,specialty,service_name` в `missing`) — это ответ на кнопку «Записаться на приём».
- Не ход выбора из показанного списка (`pending_answer.picked` услуги или филиала — пункт уже выбран).
- Ответы на шаги филиала, даты, ФИО — структурные (STRUCTURED_REPLY), их разбирают правила, как сейчас; LLM не зовётся.

Один вызов на ход; результат хранится в переменной контекста хода (как разбор цены), дозаполнение того же хода читает его.

## 5. Сбой LLM

`unavailable` / `invalid` / бюджет исчерпан:

- узел `booking_target` в `[MESSENGER_ROUTER] llm_fail_offer` — **честный оффер** «Не смог точно разобрать вопрос — чтобы не
  ошибиться, ответит оператор» (тот же текст и механизм, что у узлов `topic`, `facet`, `role_pick`; BUG-2026-10-27-LLM-QUEUE-GIVES-UP);
- узла нет — разрез по буквам, как без выключателя (поведение базы байт в байт).

Замер (стенд, LLM лежит целиком — режим `down`, код `8148d05`): без узла on = off байт в байт (кнопки 0 / 1008, dev 0 / 867); с
узлом — оффер на 125 / 1008 кнопок (102 из 113 ходов листа «Записаться на приём») и 68 / 867 dev. В базе на этих ходах — 50
уточнений, 26 ответов, 15 вариантов с ценами, 9 принятых записей, 34 оффера / перевода. Узел при полном сбое снимает и верные
ответы правил, поэтому по умолчанию — без узла (как `topic` и `role_pick` на проде); включать ли — решение владельца (§10, п. 1).

Без узла на листе «Записаться на приём» 15 из 113 ходов кончаются вопросом цели («уточните: к какому врачу/специалисту или на какую
услугу»). Следующий ход при лежащей LLM стенд одного хода не видит. Предусловие включения (консилиум 28.10) — проверить диалогом в
два хода, что запись кончается оффером, а не тупиком; тупик — повод для политики сбоя на шаге цели (на класс), §10, п. 4.

## 6. `appointment_flow_active`, когда тему записи решает LLM

Поток стартует в `orchestrator` штатно: план записи с недостающими слотами ставит `appointment_flow_active` и фазу COLLECTING.
С LLM-темой он не стартовал не из-за метки, а из-за свободного `service_name` классификатора → гард B′ (сбрасывает поток, оффер).
Под `booking_target_llm = on` цель хода — из разметки: «Хочу записаться к врачу» → `target = []` → цели нет → вопрос «к какому
врачу или на какую услугу» → поток активен (как у правила). Действие `book` из разметки ставится и тогда, когда классификатор
вернул `appointment_action = null`. Отдельного флага держать не нужно; инвариант — в тесте класса (§8).

## 7. Цена

- +1 вызов LLM (`generate_structured`, в бюджете хода) на первом ходе записи и на ответе на вопрос цели. Прод 14–28.10: ветка
  `rule_appointment` — 13 из 767 ходов пациентов, `flow_prelock` на вопросе цели — того же порядка (≈ 2–4 % ходов).
- Бюджет хода — 3 решения: разметка (1) + суд услуги (1) + роль (возвращается, если не меняла ход). Исчерпание видно в строке
  хода (`tu_decisions_denied`), проверяется карточкой.
- Таймаут — как у разметки цены (5 с + 0,25 с на слово, очередь 1,5 с).

## 8. Тест на класс (через `messenger_generate_once`)

Инварианты:
1. Филиал, названный в реплике вместе с целью и датой, — в заявке; бот не спрашивает филиал (К13). Филиал, которого нет в
   справочнике, в слот не пишется — бот показывает филиалы по данным (К8).
2. Слово адреса не становится услугой, номер дома или «узи 2» — не филиал.
3. «Хочу записаться к врачу» (цели нет) — вопрос цели, поток записи активен, и когда тему решала LLM (`rule_appointment` в
   `topic_by_llm`), и когда правило.
4. Отмена / перенос, найденные правилом, разметка в «записаться» не превращает.
5. Сбой разметки: без узла — ответ базы байт в байт; с узлом `booking_target` — честный оффер.
6. `booking_target_llm = off` — LLM разметки не зовётся, ответ байт в байт как база.

## 9. Замер и снятие правил

- Контроль `off` (повтор из кэша) против `s19all_*` — 0 отличий.
- Карточка `on`: лист «Записаться на приём» (`buttons_v1`) и ходы `rule_appointment` dev / test; вариант «+ `rule_appointment` в
  `topic_by_llm`» — отдельно. Встречный свип — `sweep_rule_appointment.jsonl` (120 реплик прода). Отличия — судья вслепую.
- Готово: К13, «Хочу записаться к врачу → Пока не понял» и «услуга есть, бот говорит нет» не хуже базы, чужих цен не прибавилось.
- После недели `on`: снять разрез цели по буквам (`_fill_appointment_entities` для записи, сущности ветки `rule_appointment`,
  сырой филиал `looks_like_branch_hint` в записи); храповик правил — вниз. `rule_appointment` в `topic_by_llm` — отдельным
  решением по карточке.

## 10. Решения на проверку владельцем

1. Сбой разметки — оффер (узел `booking_target` в `llm_fail_offer`) или разрез по буквам? При полном сбое LLM узел даёт оффер на
   12 % ходов кнопок (§5); рекомендую без узла, пока LLM-путь не отработал неделю.
2. Несколько целей в одной реплике («ЭхоКГ и Холтер») — слова групп через «и» одной фразой судье услуги (он показывает варианты
   на выбор, принцип «при неоднозначности — список»). Альтернатива — сразу оператор.
3. Включать вместе с `rule_appointment` в `topic_by_llm` или по одному — по карточке.
4. **Предусловия включения (консилиум 28.10, п. «г»):** не в набор 19 — отдельной выкаткой, не в пакете (набор 20+). До неё:
   поимённый разбор 7 «хуже» с решением на класс, без микропатчей; встречный свип по прод-репликам «запиши / запишите на …» (класс,
   на котором `rule_appointment` списком провалился — поток не стартует; в нынешнем свипе таких 9 из 120, без предыдущего хода);
   проверка при упавшей LLM (§5). Подробности — журнал, STEP-2026-10-28-BOOKING-TARGET-BY-MEANING.
