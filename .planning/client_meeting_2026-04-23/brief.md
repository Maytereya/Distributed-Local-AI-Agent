## 3. Почему это не «скрипт» — аргументы на возражения

**Базовый тезис:**
> «Любая из этих функций — 20 строк для одного сценария. Но у нас живой бот: 653 теста, 62 эталонных диалога, 8 работающих сценариев. Новая функция должна (а) не сломать существующее, (б) работать на реальных запросах пациентов, (в) корректно вести себя при сбоях API. Это 80% работы. Код — 20%.»

**Конкретные примеры на случай «это же просто»:**

**Корзина анализов** — не `split по запятой`:
- Пациент пишет «ОАК, ферритин и ещё витамин D срочно» — 3 позиции, одна группа, модификатор только к одной.
- У услуг разные `priceUnitId` — штука/панель/выезд. Сложить напрямую = неверный чек.
- Акции vs прайс (на слайде 7: «390 руб / акция 87 руб») — что складывать?
- «Уберите витамин, добавьте B12» — это состояние корзины, не один запрос.

**Геолокация** — не `haversine`:
- В TG/WA/MAX гео передаётся по-разному — 3 адаптера, не 1.
- Ближайший филиал ≠ подходящий: флюоро/маммо только в 2 филиалах из N (наш недавний фикс `fix(address+price)` — живое доказательство).
- Пациент редко даёт гео → нужен fallback через район/метро + geocoding.

**Акции + LLM** — не `дёрнуть API`:
- LLM не должна галлюцинировать акции — это юридический риск. Нужны guardrails и citation.
- «Есть скидка на ОАК?» vs «что у вас нового?» — разные интенты, разная маршрутизация.
- Кэш с TTL и инвалидацией — иначе бот неделю после акции её ещё продаёт.

**Адрес по процедуре** — самая дешёвая, но не ноль:
- Когда Nayka даст поле, нужно **снять** наши ручные фиксы (флюоро/маммо/эндоскопия) — иначе двойная логика.
- Валидация пустого/противоречивого значения → fallback-контракт.

## 4. Формат ТЗ — условие старта

**Прямая формулировка для клиента:**
> «По опыту прошлых итераций — большая часть переделок возникала из-за того, что критерии "готово" формулировались уже в процессе. Чтобы не повторять это — фиксируем ТЗ по каждой функции в формате, который пришлём. Это снимает 30–40% трудозатрат на уточнения и позволяет дать точный срок и цену, а не вилку.»

**Что отдаём клиенту:**
- Шаблон ТЗ (7 разделов: цель, вход, выход, источники, краевые случаи, приёмка, вне зоны).
- **Заполненный пример** по функции «Запись к врачу» — чтобы было что редактировать, а не писать с нуля.

**Что просим у клиента заполнить самому по каждой новой функции:**
- 5–10 реальных фраз пациентов на входе (не придуманных).
- 10 эталонных диалогов «вход → ожидаемый выход» для приёмки.
- Список краевых случаев (неоднозначность, модификаторы, пустой результат).

**Жёсткое правило — донести мягко:**
> Пока не согласованы пункты «Краевые случаи» и «Приёмка» — работа по функции не стартует. Это единственный способ избежать бесконечных правок.

## 5. Вопросы клиенту на созвоне

Минимум без них не закрыть цену:

1. **MAX** — кто поднимает бота в реестре? Нужна ли модерация/верификация со стороны платформы?
2. **Акции** — есть ли API? Если нет — куда администраторы клиники вносят промо (CRM? сайт?)
3. **Адрес по процедуре** — сроки появления поля от Nayka, формат (id филиала / строка / массив)?
4. **Гео** — радиус/город по умолчанию; как быть, если филиалов в городе пациента нет?
5. **SLA/нагрузка MAX** — ожидаемое количество обращений, чтобы заложить инфру.
6. **Приоритет функций** — если бюджет ограничен, что делаем первым?
