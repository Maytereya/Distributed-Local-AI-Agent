# ТЗ: Запись к врачу

> **Как пользоваться этим документом:**
> Это заполненный пример ТЗ по одной из уже реализованных функций.
> Используйте его как шаблон: копируйте структуру (7 разделов), заменяйте содержимое под новую функцию.
> Красным выделены места, которые на практике чаще всего упускают и из-за которых возникают переделки.

---

## 1. Цель

**Для пациента:** записаться к нужному врачу в удобное время, не звоня в колл-центр.

**Для клиники:**
- Снять нагрузку с колл-центра по типовым записям.
- Получить в CRM/АМО валидную карточку записи, которую оператор только подтверждает, а не собирает с нуля.

**Критерий «заработало»:**
- Пациент от запроса «хочу к кардиологу» до подтверждённой заявки доходит за ≤5 сообщений.
- Оператор получает карточку с: ФИО пациента, ФИО врача, адрес, дата, время — без пустых полей.
- 10 эталонных диалогов из раздела 6 проходят автоматическую проверку.

---

## 2. Вход

### 2.1. Сценарии запуска (как пациент инициирует запись)

Явный запрос:
- «Хочу записаться к кардиологу»
- «Запишите меня к Хальметовой»
- «Нужна запись на приём»

Переход из другого сценария:
- Смотрел расписание → «Запишите на 14:00»
- Спрашивал про стоимость → «Давайте запишемся»
- Спрашивал про специалиста → «Подойдёт, запишите»

### 2.2. Каналы

- [x] Telegram
- [x] WhatsApp
- [ ] MAX (добавить в отдельной итерации)

### 2.3. Границы — что НЕ обрабатываем ботом

- Запись на процедуры с предоплатой → сразу handoff оператору.
- Запись по ДМС → handoff (нужна проверка полиса).
- Запись детей до 3 лет → handoff (требуется родитель).
- Перенос существующей записи → handoff.

## 3. Выход

### 3.1. Последовательность шагов бота

**Шаг 1 — поиск врача/специальности:**
```
1. <ФИО врача 1> (<Специальность>) — <цена> руб.; <статус слота>
2. <ФИО врача 2> ...
Если нужно, покажу подробное расписание любого из этих врачей.
```

**Шаг 2 — расписание выбранного врача:**
```
1. <ФИО врача>
Адреса приема: <адрес>
Ближайшее актуальное расписание сейчас есть в филиале: <адрес>
<адрес>:
• <дата>: свободно в <слот1>, <слот2>, <слот3>
Если нужно записаться — напишите удобное время.
```

**Шаг 3 — запрос ФИО пациента:**
```
Укажите, пожалуйста, ФИО пациента для оформления заявки на запись.
```

**Шаг 4 — карточка подтверждения:**
```
Запись: <ФИО пациента>, приём к врачу <ФИО врача>, <адрес>, <дата>, <время>. Подтверждаете?
```

**Шаг 5 — финальное сообщение + handoff:**
```
Запись: <ФИО пациента>, приём к врачу <ФИО врача>, <адрес>, <дата>, <время>.
Передаю заявку оператору для окончательного подтверждения записи.
🤝 handoff: передача оператору
```

### 3.2. Что уходит оператору (структурированная карточка)

```json
{
  "patient_name": "Рахманов Владимир",
  "doctor_name": "Хальметова Алина Алексеевна",
  "doctor_specialty": "Кардиолог",
  "clinic_address": "г. Самара, пр. Ленина, 5",
  "appointment_date": "2026-04-24",
  "appointment_time": "12:00",
  "source_channel": "telegram",
  "patient_contact": "<tg_username или phone>",
  "dialog_id": "<id для возврата в диалог>"
}
```

### 3.3. Ответы, когда данных нет

- **Врача нет в базе:** «К сожалению, такого врача у нас не принимает. Вот кто ещё принимает по специальности: ...»
- **Врач есть, но слотов нет:** «У <ФИО> сейчас нет свободных слотов. Показать расписание других врачей специальности?»
- **Специальности нет в клинике:** «К сожалению, клиника не оказывает приёмы по этой специальности.»
- **API Nayka недоступен:** отдаём последний валидный кэш расписания + пометка «данные могут быть неактуальны, оператор уточнит»; handoff оператору не блокируется.

## 4. Источники данных

| Что | Откуда | Endpoint / поле |
|---|---|---|
| Список врачей по специальности | Nayka API | `GetDoctorsBySpecialty` |
| Расписание врача | Nayka API | `GetDoctorSchedule` |
| Адреса филиалов, где принимает врач | Nayka API | `GetDoctorInfo.addresses` |
| Цена приёма | Nayka API | `GetServicePrice` (услуга «приём <специальность>») |
| Профиль врача (текст) | Nayka API | `GetDoctorInfo.doctorInfo` |
| Создание заявки оператору | Внутренняя очередь handoff | `POST /handoff/create` |

**Требования к API клиники (зафиксировать явно):**
- Время ответа p95 ≤ 2 сек.
- Расписание обновляется в Nayka не реже 1 раза в 5 минут.
- При изменении расписания — принудительная инвалидация кэша бота (webhook или TTL ≤ 5 мин).

## 5. Краевые случаи ⚠️

**Это самый важный раздел. Именно здесь возникают переделки, если не обсудили заранее.**

### 5.1. Неоднозначный запрос

| Пациент пишет | Что должен делать бот |
|---|---|
| «Хочу к Иванову» (несколько Ивановых) | Уточнить: «У нас принимают: Иванов И.И. (Кардиолог), Иванов П.П. (Уролог). Кого именно?» |
| «Запишите к кардиологу» (без имени) | Показать список кардиологов по приоритету (шаг 1) |
| «К любому кардиологу» | Выбрать первого с ближайшим свободным слотом, предложить карточку подтверждения |
| «Подешевле» | Отсортировать по цене возрастания в рамках специальности |

### 5.2. Проблемы со временем

| Пациент пишет | Что должен делать бот |
|---|---|
| «На следующую неделю» | Показать все свободные слоты с понедельника по воскресенье следующей недели |
| «Завтра в 10» | Проверить конкретный слот; если занят — предложить ближайшие ± 1 час |
| «В выходные» | Показать только слоты сб/вс |
| Указано прошедшее время | «Это время уже прошло. Ближайшее свободное: ...» |
| Слот только что занят другим пациентом | «К сожалению, слот только что заняли. Ближайшие свободные: ...» |

### 5.3. Проблемы с ФИО

| Ситуация | Поведение бота |
|---|---|
| Пациент ввёл одно слово («Владимир») | Уточнить: «Нужны фамилия и имя, для оформления заявки» |
| Пациент ввёл 4+ слов | Принимать как есть, не резать |
| Пациент ввёл ник/ерунду («vovan228») | Уточнить: «Пожалуйста, укажите ФИО для оформления заявки» |
| Пациент ввёл ФИО на английском | Принимать как есть, передавать оператору для уточнения |

### 5.4. Отказы и отмены

| Пациент пишет | Поведение бота |
|---|---|
| «Не, передумал» на шаге подтверждения | «Запись отменена. Если передумаете — напишите.» (состояние очищается) |
| «Давай другое время» после карточки подтверждения | Вернуться к шагу 2 (расписание) с тем же врачом |
| «Давай к другому врачу» | Вернуться к шагу 1 (список врачей по той же специальности) |
| Молчание >24 часов после карточки подтверждения | Заявка не создаётся, состояние очищается |

### 5.5. Технические сбои

| Ситуация | Поведение бота |
|---|---|
| Nayka API не отвечает на шаге 1 | Отдать кэш (если ≤30 мин); если нет — handoff с сообщением «не могу получить расписание» |
| Nayka API не отвечает на шаге 5 (создание заявки) | Карточка сохраняется локально + handoff; оператор создаёт заявку вручную |
| Бот потерял контекст (перезапуск сервера) | При следующем сообщении пациента — переспросить с последнего неподтверждённого шага |

## 6. Приёмка — эталонные диалоги

Функция считается принятой, если **все 10 диалогов** ниже автоматически воспроизводятся ботом со 100% совпадением по структуре ответа (значения полей могут отличаться — проверяется формат).

### Диалог 1 — прямая запись к конкретному врачу
```
П: Запишите меня к Хальметовой
Б: [шаг 2 — расписание]
П: 25 апреля в 14:00
Б: [шаг 3 — запрос ФИО]
П: Иванов Иван
Б: [шаг 4 — карточка]
П: да
Б: [шаг 5 — handoff]
```

### Диалог 2 — через специальность
```
П: Хочу к кардиологу
Б: [шаг 1 — список]
П: Первого
Б: [шаг 2 — расписание]
...
```

### Диалог 3 — отказ на подтверждении
```
...
Б: [шаг 4 — карточка]
П: нет
Б: Запись отменена. Если передумаете — напишите.
```

### Диалог 4 — смена врача после выбора
```
...
Б: [шаг 2 — расписание]
П: давайте другого врача
Б: [шаг 1 — список заново]
```

## 7. Вне зоны ответственности (явно НЕ делаем в этой итерации)

Фиксируем, чтобы потом не всплыло «а вот ещё это добавьте»:

- Запись нескольких пациентов за один диалог (один пациент = одна запись).
- Запись сразу на несколько процедур/специалистов «в пакете».
- Онлайн-оплата записи в чате (только handoff оператору).
- Напоминания пациенту накануне записи (отдельная функция).
- Отмена/перенос уже созданной записи из бота (отдельная функция).
- Проверка ДМС-полиса и условий страховки.
- Запись на выезд/на дом.
- Запись по направлению от другого врача с учётом направления.
