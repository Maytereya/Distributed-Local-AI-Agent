# PRICE Bug Tracker

Документ фиксирует проблемные кейсы `PRICE` / `service_bundle_info` в `messengers_router`.
Каждый пункт закрывается отдельно: анализ -> фикс -> тесты -> серверная проверка.

## Цель

- Не смешивать рабочий backlog по `PRICE`-дефектам с [`ARCHITECTURE_STATUS.md`](/Users/maxten/Dev/Distributed-Local-AI-Agent2/messengers_router/ARCHITECTURE_STATUS.md).
- Вести единый список проблем, их причин, плана фикса и статуса.
- Закрывать кейсы по одному, но держать весь набор из 13 пунктов в одном месте.

## Статусы

- `OPEN` — дефект подтвержден, работа не начата.
- `IN_PROGRESS` — идёт реализация фикса.
- `FIXED_LOCAL` — фиксы и тесты локально готовы.
- `FIXED_SERVER` — поведение подтверждено на сервере.
- `REGRESSION` — кейс ломался повторно после предыдущего фикса.
- `WONT_FIX` — принято решение не исправлять в текущем контуре.

## P01. Стоимость гепатита

**Статус:** `FIXED_LOCAL`

**Запрос:** `стоимость гепатита`

**Факт до фикса:**
Бот схлопывал запрос в одну top-услугу вместо семейства анализов по гепатитам.

**Локальный результат после фикса:**
Включен family-mode: бот возвращает до 10 релевантных строк по гепатитам и подсказку `Чтобы показать все, напишите: "все"`.

**Ожидание:**
Бот должен либо:
- показать релевантные варианты по гепатитам;
- либо задать уточнение по типу гепатита.

**Класс дефекта:** `family_query_collapse`

**Корневая причина:**
Generic disease-query приземлялся в одну каноническую строку через `resolve_price_service_name_from_catalog()`, а family-mode отсутствовал.

**Что менять:**
- внедрён family-mode для generic price-query;
- добавлен stateful follow-up `все`;
- patient-facing rendering теперь умеет выводить family variants.

**Тесты:**
- unit: family ranking для `гепатит`;
- service: `price_info()` / `service_bundle_info()` на `стоимость гепатита`;
- endpoint smoke: `стоимость гепатита`.

**Примечание:**
В прайсе много строк по гепатитам; проблема не в отсутствии данных.

**Серверная проверка:**
Подтверждено прогоном `run_remote_eval.sh` (`run_id=1775676454`): `stage5 PRICE 13/13`, `critical 46/46`.

**Статус:** `FIXED_SERVER`

**Ожидание:**

**Тесты:**
- unit: catalog-driven `service_kind` для `АлАТ`;
- service: `service_bundle_info()` / `price_info()` без врачей;
- endpoint smoke: `стоимость алат`.

**Примечание:**

## P03. Стоимость ВИЧ

**Статус:** `FIXED_SERVER`

**Запрос:** `стоимость вич`

**Факт до фикса:**
Бот показывал экспресс-тест как один основной вариант, хотя в прайсе есть и обычный анализ крови на ВИЧ.

**Локальный результат после фикса:**
`price_info("стоимость вич")` возвращает оба релевантных варианта: кровь на ВИЧ и экспресс-тест. Экспресс больше не доминирует в одиночку.

**Ожидание:**
Бот должен показывать релевантные варианты по ВИЧ, а не только экспресс.

**Класс дефекта:** `family_query_collapse`

**Корневая причина:**

**Что менять:**
- family selection для инфекционных анализов;
- понижение приоритета `экспресс`, если его явно не просили.

**Тесты:**
- unit/service: `test_price_info_hiv_returns_multiple_relevant_variants`;
- локальный smoke: `price_info("стоимость вич")`.

**Примечание:**
Это не data issue: в прайсе есть как минимум экспресс и обычная кровь на ВИЧ.

По умолчанию должен приоритизироваться обычный лабораторный анализ витамина D, а не генетика.

Query-кандидаты типа `витамина` слишком общие, а semantically-aware приоритетов между лабораторией и генетикой нет.

**Что менять:**
- токенизацию `витамин_<код>`;
- штрафы на генетику и пакетные/маркетинговые строки;
- более жёсткое сопоставление compound-токенов.

**Тесты:**
- unit: scoring `витамин D`;
- service: `price_info()` на `стоимость витамина д`;
- endpoint smoke: `стоимость витамина д`.

**Примечание:**
Тут нужен не regex-костыль, а нормальная бизнес-приоритизация типа анализа.

## P09. Стоимость приема хирурга

**Статус:** `FIXED_LOCAL`

**Запрос:** `стоимость приема хирурга`

**Факт до фикса:**
По умолчанию бот показывал `повторный` прием, а не `первичный`.

**Локальный результат после фикса:**
`price_info("стоимость приема хирурга")` выводит `первичный` прием первым, затем `к.м.н.` и только после этого повторный/домашние варианты.

**Класс дефекта:** `consultation_priority_missing`

**Корневая причина:**
Для консультаций нет бизнес-приоритета. При одинаковом score tie-break идёт по длине названия/цене, а не по медицинскому смыслу.

**Что менять:**
- явный consultation priority:
  - `первичный > повторный`
  - base > `к.м.н.`
  - очный > `на дому`

**Тесты:**
- unit/service: `test_price_info_surgeon_prefers_primary_before_repeat_and_home`;
- local smoke: `price_info("стоимость приема хирурга")`.

**Примечание:**
Тот же класс дефекта влияет и на другие консультационные кейсы.

## P12. Стоимость постановки пломбы

**Статус:** `OPEN`

**Запрос:** `стоимость постановки пломбы`

**Факт до фикса:**
Бот выбирал `Цитомегаловирус [п\кол.]`.

**Локальный результат после фикса:**
Короткие служебные токены больше не участвуют в soft fuzzy; кейс больше не уходит в `ЦМВ`.

**Ожидание:**
Бот должен показывать стоматологические услуги по постановке пломбы.

**Класс дефекта:** `soft_token_fuzzy_false_positive`

**Корневая причина:**
Мягкий prefix-match считает токен `п` из `п\кол.` достаточным совпадением для `постановки/пломбы`, из-за чего CMV и реальные стоматологические строки получают одинаковый score.

**Что менять:**
- запретить soft fuzzy для коротких токенов;
- сохранять только точные совпадения для коротких и compound-токенов.

**Тесты:**
- unit: scoring `пломба` против `Цитомегаловирус [п\кол.]`;
- service: `price_info()` / `service_bundle_info()` на `стоимость постановки пломбы`;
- endpoint smoke: `стоимость постановки пломбы`.

**Примечание:**
Это один из базовых системных scoring-багов.

**Серверная проверка:**
Подтверждено прогоном `run_remote_eval.sh` (`run_id=1775676454`): `stage5 PRICE 13/13`, критикал зелёный.

**Класс дефекта:** `doctor_prices_source_pollution`

**Корневая причина:**
Doctor-layer пропускает нерелевантные строки `doctor_prices` из-за мягкого match по токенам вроде `под`, `кат`.

**Что менять:**
- ужесточить doctor-level matching;
- для хирургических операций доверять только exact `serviceHomecode` или validated specialty.

**Тесты:**
- unit: doctor row filtering на пластической хирургии;
- service: `service_bundle_info()` без онкологов/урологов;
- server/manual: smoke.

**Примечание:**
Проблема комбинированная: и scoring, и грязный `doctor_prices`.

## Общие классы дефектов

Подтвержденные системные проблемы:

- мягкий fuzzy-match по коротким токенам даёт ложные совпадения;
- `service_kind` для части лабораторных анализов определяется как `doctor`;
- family-mode для generic medical queries отсутствует;
- consultation priority по умолчанию не отражает бизнес-смысл;
- `doctor_prices` содержит нерелевантные привязки врачей к услугам;
- stale-context всё ещё может доминировать над новым `PRICE`-запросом;
- у `УЗИ` не хватает нормализации синонимов и детского/взрослого приоритета.
