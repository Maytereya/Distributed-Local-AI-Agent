# Operator Issues Inbox (Messenger Bot)

Черновой реестр проблем по скриншотам/диалогам от операторов.

Цель файла:
- быстро фиксировать симптомы и воспроизведение;
- не потерять контекст до отдельного анализа;
- затем превратить записи в ТЗ/issue-list для рефакторинга.

## ISSUE-001: Некорректный переход в карточку врача в сценариях УЗИ/анализов

### Источник
- Скриншоты из Telegram (`NaukaTestingBot`) от оператора.

### Симптомы
1. На вопрос про стоимость УЗИ бот отвечает ценой (возможна некорректная цена, требует проверки).
2. На follow-up вопрос `Где можно сделать данное исследование` бот вместо адресов/филиалов выводит карточку врача (`Паничева Ольга Николаевна`).
3. На запрос `Какие анализы сдать на сахарный диабет` после уточнения города (`Самара`) бот снова выводит карточку того же врача вместо подбора анализов.

### Почему это критично
- Смешиваются домены: `PRICE / ADDRESS / TEST_ASSIST` и `DOCTOR_INFO`.
- Пользователь получает не тот тип ответа (врач вместо адресов/анализов).
- Высокий риск потери доверия и ложных консультационных ответов.

### Минимальное воспроизведение (по скринам)
#### Вариант A (УЗИ)
1. Пользователь: `Сколько стоит УЗИ органов малого таза`
2. Бот: отвечает стоимостью (`1350 руб.`) и предлагает запись
3. Пользователь: `Где можно сделать данное исследование`
4. Бот: показывает врача (`Паничева Ольга Николаевна`) вместо адресов филиалов

#### Вариант B (подбор анализов)
1. Пользователь: `Какие анализы сдать на сахарный диабет`
2. Бот: `Из какого города вы обращаетесь?`
3. Пользователь: `Самара`
4. Бот: показывает врача (`Паничева Ольга Николаевна`) вместо рекомендаций/подбора анализов

### Детализированное воспроизведение (реальный лог, 26.02)
Ниже важная цепочка, показывающая, что ошибка не локальная, а контекстная:

1. Пользователь: `Как работает врач Комарова`
2. Бот: показывает карточку Комаровой
3. Пользователь: `Расписание врача`
4. Бот: показывает расписание Комаровой
5. Пользователь: `Расписание паничевой`
6. Бот: показывает расписание Паничевой
7. Пользователь: `Сколько стоит узи органов малого таза`
8. Бот: отвечает ценой `1350` и предлагает запись
9. Пользователь: `Где можно сделать данное исследование`
10. Бот: вместо адресов снова показывает карточку Паничевой
11. Пользователь: `Какие анализы сдать на сахарный диабет`
12. Бот: спрашивает город (`Из какого города вы обращаетесь?`)
13. Пользователь: `Самара`
14. Бот: вместо подбора анализов снова показывает карточку Паничевой
15. Пользователь: `Результат анализов ВГ 811`
16. Бот: корректно переходит в `TEST_RESULT` и просит данные
17. Пользователь: `Лиходкина,1977,ВГ,811`
18. Бот: корректно формирует ссылку на результат

### Что это показывает дополнительно
1. Ошибка концентрируется в переходах:
- `DOCTOR_SCHEDULE/DOCTOR_INFO -> PRICE -> ADDRESS`
- `DOCTOR_* -> TEST_ASSIST (после города)`
2. При этом `TEST_RESULT` в этом же диалоге работает корректно, то есть проблема не в общем "падении" сессии, а в неправильном удержании/переключении интентов и сущностей врача.
3. Высока вероятность залипания `doctor_name`/doctor-context (Паничева) и doctor-intent override поверх новых доменов (`ADDRESS`, `TEST_ASSIST`).

### Предварительная классификация проблемы
- `context bleed / stale doctor context`
- `wrong intent routing after follow-up`
- возможно `secondary intent queue` или `doctor override` срабатывает вне домена врача
- `doctor context not reset on explicit non-doctor intents` (`Где сделать исследование`, `Какие анализы сдать...`)

### Что проверить в коде (для последующего анализа)
- `messengers_router/router.py`
  - приоритеты label override (doctor-related promotion)
  - обработка follow-up после `PRICE`, `TEST_ASSIST`, `ADDRESS`
  - сохранение/очистка `doctor_name`, `_last_label`, `_secondary_queue`
- `messengers_router/policies.py`
  - `apply_verified_doctor_override(...)`
  - intent dominance rules для `PRICE / ADDRESS / TEST_ASSIST / DOCTOR_INFO`
- `messengers_router/flow_policy.py`
  - context action / pending override / secondary follow-up
- `messengers_router/services.py`
  - источники цены по УЗИ (проверить корректность цены и соответствие услуги)
  - логика подбора адресов для диагностики/УЗИ vs врачей

### Ожидаемое поведение
1. Вопрос `Где можно сделать данное исследование` после ответа по цене УЗИ:
- бот должен отдать адреса/филиалы (и при необходимости уточнить город), а не врача.
2. Вопрос `Какие анализы сдать на сахарный диабет`:
- бот должен вести сценарий `TEST_ASSIST` (подбор анализов), а после города — дать релевантный ответ по анализам/направить по сценарию, но не переключаться в карточку врача.
3. В длинной сессии со сменой врачей (`Комарова` -> `Паничева`) последующие запросы про УЗИ/анализы не должны наследовать doctor-intent только потому, что раньше в контексте был врач.

### Статус
- Зафиксировано, не разобрано.

## ISSUE-003: Каскадная потеря контекста в диалоге (терапевт -> адрес -> ФКС -> Тюрин -> test result -> онколог -> УЗИ -> операция -> ДМС)

### Источник
- Текстовый лог диалога от оператора (25.02, сценарий начинается с `Терапевт`).

### Симптомы (по шагам)
1. После выдачи списка терапевтов пользователь пишет `Нужен другой адрес`.
- Бот уходит в сценарий адресов и после города (`Самара`) выдает полный список филиалов (32 адреса).
2. После короткой реплики `Нужен` бот снова показывает список терапевтов (возврат в старый врачебный контекст без явного запроса).
3. Пользователь переключается на `Записаться на фкс`.
- Бот отвечает списком адресов для записи на ФКС (это выглядит допустимо).
4. Пользователь пишет `Тюрин`.
- Бот внезапно переключается в `TEST_RESULT` и просит данные для результатов анализов (совершенно нерелевантно).
5. Пользователь пишет `Онколог`.
- Бот снова показывает тех же терапевтов (старый контекст залип/домены смешались).
6. Пользователь пишет `Узи молочных желез`.
- Бот отвечает шаблоном записи на УЗИ (допустимо).
7. Пользователь пишет `Операция на сустав`.
- Бот отвечает `Есть возможность записи на Сустав...` (некорректная нормализация услуги: обрезал до `Сустав`).
8. Пользователь пишет `Дмс`.
- Бот повторяет прошлый ответ про `Сустав` (залипание предыдущего `service_name`, новая тема не распознана).

### Почему это критично
- Бот теряет управление диалогом после нескольких переключений темы.
- Наблюдается "залипание" сущностей (`doctor/specialty/service`) и перенос в новые интенты.
- Пользователь получает нерелевантные ответы, что делает диалог практически непригодным без оператора.

### Предварительная классификация проблемы
- `multi-turn context corruption`
- `stale entity reuse` (старые `doctor_name/specialty/service_name` переносятся в новый запрос)
- `wrong intent override` (короткие слова/фамилии переключают в нерелевантный flow)
- `service phrase over-truncation / bad normalization` (`Операция на сустав` -> `Сустав`)
- `topic switch not resetting state`

### Минимальное воспроизведение (сжатая версия)
1. `Терапевт`
2. `Нужен другой адрес`
3. `Самара`
4. `Нужен`
5. `Записаться на фкс`
6. `Тюрин`
7. `Онколог`
8. `Узи молочных желез`
9. `Операция на сустав`
10. `Дмс`

### Что проверить в коде (для последующего анализа)
- `messengers_router/router.py`
  - очистка state при смене темы (`context_action`, `_clear_flow_state`, `_clear_topic_state`)
  - условия flow override (`appointment_flow_active`, pending override)
  - когда и почему `TEST_RESULT` может срабатывать на фамилию (`Тюрин`)
  - поведение после коротких реплик (`Нужен`, `Тюрин`, `Дмс`)
- `messengers_router/recovery_policy.py`
  - обработка коротких/неполных реплик и удержание/сброс контекста
- `messengers_router/policies.py`
  - `extract_service_phrase(...)` и нормализация услуги (`Операция на сустав`)
  - интент-детекторы `TEST_RESULT`, `DOCTOR_INFO`, `APPOINTMENT`, `PRICE`, `ADDRESS`
  - quick-fill (что именно подхватывает из коротких слов)
- `messengers_router/entity_grounder.py`
  - достаточно ли он очищает нерелевантные сущности при смене label
  - нужны ли дополнительные правила “drop stale entities on topic switch”
- `messengers_router/flow_policy.py`
  - pending override / context action override в цепочке быстрых переключений

### Ожидаемое поведение
1. `Нужен другой адрес` после списка терапевтов:
- бот должен уточнить адрес/город в контексте текущего сценария, но без “разрушения” специальности/выбранного списка.
2. `Тюрин`:
- бот должен трактовать как фамилию врача/уточнение врача (или спросить уточнение), но не переключаться в результаты анализов.
3. `Операция на сустав`:
- бот не должен редуцировать услугу до слишком общего `Сустав` без подтверждения.
4. `Дмс`:
- бот должен распознать новую тему (или уточнить, что именно интересует по ДМС), а не повторять ответ по предыдущей услуге.

### Дополнительное наблюдение
- В одном диалоге проявляются сразу несколько классов ошибок, поэтому этот кейс полезен как regression-сценарий для stress-test длинной сессии.

### Статус
- Зафиксировано, не разобрано.

## ISSUE-002: Сценарий "прием уролога" уходит в общий адресный/докторский шум, ломается фильтрация по специальности и цене

### Источник
- Текстовый лог диалога + комментарий оператора (25.02).

### Симптомы
1. На запрос `Прием уролога` бот сначала спрашивает город (нормально), но после города (`Самара`) выдает огромный список всех филиалов города вместо уточнения врача/уролога или релевантных точек приема.
2. На ввод `Уролог` бот показывает список урологов (частично ожидаемо), но далее при запросе `Михайлов уролог расписание`:
- выводит врачей по совпадению `Михайлов` из других специальностей (гинеколог, онколог, УЗИ и т.д.);
- не удерживает фильтр по специальности `уролог`;
- в выдаче появляется врач из Оренбурга (неожиданный регион/шум в контексте Самары).
3. На запрос стоимости (`Уролог цена приема`, `Прием уролога цена`) бот зацикливается на фразе:
- `Скажите, пожалуйста, название услуги/анализа — я уточню стоимость.`
- не умеет распознать `прием уролога` как цену услуги/приема.

### Почему это критично
- Пользовательский путь по популярному сценарию (прием специалиста) становится длинным и нестабильным.
- Бот не удерживает выбранную специальность/город и смешивает врачей по совпадению фамилии.
- Цена приема специалиста не отрабатывается, хотя это базовый запрос.

### Минимальное воспроизведение (по логу)
1. Пользователь: `Прием уролога`
2. Бот: `Из какого города вы обращаетесь?`
3. Пользователь: `Самара`
4. Бот: выводит полный список филиалов Самары (32 адреса)
5. Пользователь: `Уролог`
6. Бот: выводит список урологов (несколько врачей)
7. Пользователь: `Михайлов уролог расписание`
8. Бот: выдает список врачей с фамилией `Михайлов`, включая нерелевантные специальности/регион
9. Пользователь: `Уролог цена приема` / `Прием уролога цена`
10. Бот: просит назвать услугу/анализ и не может дать цену

### Комментарий оператора (суть)
- После города бот выдает все адреса, а не ведет сценарий по специалисту.
- При выборе `Михайлов` теряется фильтр `уролог`, матчится по фамилии слишком широко.
- Появляется врач из Оренбурга.
- По цене приема уролога бот не умеет продолжить диалог.

### Предварительная классификация проблемы
- `specialty context lost` (теряется контекст специальности после списка врачей)
- `doctor name matching too broad` (матч только по фамилии без доменных фильтров)
- `cross-region leakage` (попадание нерелевантного региона)
- `price intent sloting gap` (цена приема специалиста не маппится на service/doctor price query)

### Что проверить в коде (для последующего анализа)
- `messengers_router/router.py`
  - APPOINTMENT flow после фразы вида `прием <специалист>`
  - что происходит после шага `city`: почему сразу `ADDRESS` с полным списком
  - перенос контекста `specialty` в `DOCTOR_INFO -> DOCTOR_SCHEDULE`
- `messengers_router/services.py`
  - `doctors_info(...)` и `doctors_schedule_week(...)`: фильтрация по specialty + city + prior context
  - `price_info(...)`: умеет ли обрабатывать `прием уролога` как цену приема специалиста
- `messengers_router/policies.py`
  - извлечение `specialty` и сохранение в entities
  - intent dominance для `PRICE` + doctor/specialty context
  - правила для `doctor_name` vs `specialty` в запросе `Михайлов уролог расписание`
- `agent_logic_2/doctor_name_matching.py` (только чтение/анализ, без правок при текущем scope)
  - как работает матч фамилии и можно ли сужать по specialty/city на уровне вызова из `messengers_router`

### Ожидаемое поведение
1. `Прием уролога`:
- после города бот должен вести к выбору уролога/врача (или показать урологов в этом городе), а не весь список филиалов.
2. `Михайлов уролог расписание`:
- бот должен приоритезировать уролога Михайлова из текущего города/контекста;
- при неоднозначности — спросить уточнение (например, филиал), но не показывать нерелевантные специальности.
3. `Прием уролога цена`:
- бот должен распознавать это как запрос цены приема уролога и либо дать диапазон/варианты, либо попросить уточнить врача/тип приема (первичный/повторный), но не отправлять в цикл `название услуги/анализа`.

### Статус
- Зафиксировано, не разобрано.
