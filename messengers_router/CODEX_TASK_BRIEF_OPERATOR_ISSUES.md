# ТЗ для Codex: разбор и исправление ошибок мессенджер-бота по логам операторов

## 1. Контекст

Проект: пациентский мессенджер-бот клиники (`Telegram/WhatsApp`), модуль `messengers_router`.

Текущее состояние:
- бот уже работает в production-like режиме;
- есть новая архитектура (v2-пайплайн: NLU + recovery + graph/context);
- одновременно остаются ошибки маршрутизации и потери контекста в длинных диалогах.

Источник проблем:
- реальные диалоги/скриншоты от операторов;
- собраны в файл: `messengers_router/OPERATOR_ISSUES_INBOX.md`.

Дополнительный ориентир по архитектуре:
- `messengers_router/ARCHITECTURE_STATUS.md`.

## 2. Цель работы

Разобрать и исправить ошибки роутинга/контекста, выявленные в реальных диалогах, без ломки API и без деградации базовых сценариев.

Ключевая цель:
- бот должен корректно удерживать тему диалога и не “залипать” на врачебном контексте при переходе к анализам/адресам/ценам.

## 3. Scope и ограничения

### Разрешено
- менять код внутри `messengers_router/**`;
- добавлять/обновлять тесты в `tests/**` (если они относятся к `messengers_router`);
- добавлять debug/trace-данные совместимо с текущей схемой.

### Нежелательно / только чтение
- `agent_logic_2/**` (операторский бот и общие API-модули) не менять без крайней необходимости;
- можно читать для анализа (например, `doctor_name_matching.py`), но не рефакторить в этом цикле.

### Нельзя ломать
- API-контракт ответа:
  - `text`
  - `attachments`
  - `handoff`
  - `state_update`
- текущие endpoints:
  - `/api/messenger-generate`
  - `/api/messenger-generate-once`

## 4. Основные проблемы (входные данные)

Подробности см. в `messengers_router/OPERATOR_ISSUES_INBOX.md`.

### ISSUE-001 (doctor-context bleed в УЗИ/анализах)
Суть:
- после сценариев врача/расписания (`Комарова`, `Паничева`) запросы:
  - `Сколько стоит узи...`
  - `Где можно сделать данное исследование`
  - `Какие анализы сдать на сахарный диабет`
могут ошибочно возвращать карточку врача (Паничева) вместо цены/адресов/подбора анализов.

Ключевой признак:
- `TEST_RESULT` при этом работает корректно в той же сессии, значит проблема локальна в маршрутизации/контексте, а не в полном “развале” сессии.

### ISSUE-002 (прием уролога: потеря specialty / широкий матч / цена)
Суть:
- `Прием уролога` после города уходит в список всех филиалов;
- `Михайлов уролог расписание` матчится по фамилии слишком широко (включая нерелевантных врачей и регион);
- `Прием уролога цена` не распознается как запрос цены приема специалиста и зацикливается на фразе “название услуги/анализа”.

### ISSUE-003 (каскадная потеря контекста в длинной сессии)
Суть:
- в одном диалоге наблюдается цепочка ошибок:
  - возврат к старым врачам,
  - нерелевантный переход в `TEST_RESULT`,
  - неправильная нормализация услуги (`Операция на сустав` -> `Сустав`),
  - повтор ответа по прошлой услуге на новый запрос (`Дмс`).

## 5. Что нужно получить в результате

### Обязательный результат
1. Исправленные сценарии по ISSUE-001..003.
2. Набор regression-тестов (unit/integration-lite), фиксирующих воспроизведение и правильное поведение.
3. Краткое описание внесенных изменений:
- что было причиной;
- что исправлено;
- какие риски остаются.

### Желательный результат
1. Локальная диагностика (debug flags/trace), которая помогает понять:
- почему был выбран интент;
- почему удержан/сброшен контекст;
- какие сущности были отброшены как stale/invalid.
2. Снижение зависимости от точечных regex-заплаток в пользу:
- entity grounding;
- явных правил сброса topic-specific state.

## 6. Гипотезы (на что смотреть в первую очередь)

Это не требования, а приоритетные направления анализа.

### 6.1 Залипание doctor-context
Проверить:
- когда `doctor_name` / doctor-related flags остаются в state после явных non-doctor запросов;
- где doctor override/promote срабатывает поверх новых доменов (`ADDRESS`, `TEST_ASSIST`, `PRICE`).

Подозрительные места:
- `messengers_router/router.py`
- `messengers_router/policies.py` (`apply_verified_doctor_override`)
- `messengers_router/flow_policy.py`

### 6.2 Потеря specialty/city фильтра
Проверить:
- перенос `specialty` между шагами `DOCTOR_INFO -> DOCTOR_SCHEDULE`;
- сужение выборки врачей по:
  - `specialty`,
  - `city`,
  - предыдущему выбранному контексту.

### 6.3 Неверный reset state при смене темы
Проверить:
- правила topic switch (когда надо сбрасывать `service_name`, `doctor_name`, pending, flow-active флаги);
- поведение на коротких репликах (`Нужен`, `Тюрин`, `Дмс`).

### 6.4 Слотинг цены приема специалиста
Проверить:
- почему `Прием уролога цена` не превращается в корректный `PRICE`-сценарий;
- как маппить “прием <специалист>” в price-поиск:
  - через врача,
  - через специальность,
  - через шаблон услуги.

## 7. Требования к подходу (важно)

### 7.1 Не чинить только “симптом”
Нельзя ограничиться точечным regex под конкретный кейс (`Паничева`, `Михайлов`, `Тюрин`).

Нужно:
- исправлять класс ошибки:
  - stale entities,
  - wrong override precedence,
  - context switch rules,
  - overly broad doctor matching.

### 7.2 Сохранять живой диалог
При исправлениях не сломать:
- продолжение записи после показа расписания (`Самара`, `16:30`, ФИО и т.п.);
- `TEST_RESULT` сценарий с формированием ссылки;
- nonbookable сценарии (`анализы/ЭКГ`) с адресами.

### 7.3 Предпочтение модульным изменениям
Предпочтительно вносить изменения в:
- `entity_grounder.py`
- `recovery_policy.py`
- `flow_policy.py`
- `policies.py`

и только затем в `router.py`, если иначе нельзя.

## 8. Минимальный план работ (рекомендуемый)

1. Воспроизвести ISSUE-001..003 локально (через simulator/curl + debug).
2. Зафиксировать фактические `decision/plan/evidence/last_entities` на проблемных шагах.
3. Выявить механизм ошибки:
- stale entity reuse
- override conflict
- pending/flow leakage
- bad service extraction
4. Внести минимальные изменения для исправления класса ошибки.
5. Добавить regression-тесты под каждый issue (или под ключевые подшаги).
6. Проверить вручную базовые сценарии:
- врач/расписание
- запись
- анализы/подбор
- результаты анализов
- цена/адрес

## 9. Acceptance criteria (что считать “готово”)

### По ISSUE-001
1. После врача/расписания запрос `Где можно сделать данное исследование` не возвращает карточку врача.
2. После `Какие анализы сдать на сахарный диабет` + `Самара` бот не возвращает врача Паничеву.

### По ISSUE-002
1. `Прием уролога` после города не должен уходить в нерелевантный общий адресный шум без дальнейшего ведения по specialty.
2. `Михайлов уролог расписание` должен удерживать фильтр `уролог` (или спрашивать уточнение), не показывая нерелевантных врачей.
3. `Прием уролога цена` должен вести в рабочий `PRICE`-сценарий (или корректное уточнение), без зацикливания.

### По ISSUE-003
1. `Тюрин` не должен переводить в `TEST_RESULT`, если контекст не про результаты анализов.
2. `Операция на сустав` не должна нормализоваться до слишком общего `Сустав` без подтверждения.
3. `Дмс` не должен повторять ответ по предыдущей услуге.
